## 1. PROJECT OVERVIEW
**KeyPulse** is a lightning-fast, ultra-lightweight Windows hotkey manager designed for power users. 
- **Tech Stack**: C# 13, .NET 9, Avalonia UI 12.1.
- **Compilation**: Single-file `NativeAOT` (No .NET runtime dependencies).
- **OS Target**: Windows x64 Strictly (Heavily relies on Win32 P/Invoke).

## 2. CORE ARCHITECTURE & LOGIC FLOW

### Boot / Initialization (`Program.cs` & `App.axaml.cs`)
1. Executable is launched. `Program.cs` intercepts the startup arguments. Passing `run-ui` or setting `KEYPULSE_DEV_MODE=1` activates `Program.IsDevMode` (`DEVDATA_01`), running the application in a strictly isolated Developer Sandbox (`%LOCALAPPDATA%\KeyPulse_DEV`) with zero cross-contamination against the installed production app.
2. **Mutex Protection**: Checks a **session-local** `Local\KeyPulse_SingleInstance_Mutex_v1` mutex (`Local\KeyPulse_SingleInstance_Mutex_v1_DEV` in Dev Mode), created through `CreateSharedMutex` with the SDDL `D:(A;;GA;;;WD)S:(ML;;NW;;;LW)`. The **low mandatory label is load-bearing**: an object created by the elevated logon-task instance otherwise carries a High label, Windows refuses a normal-integrity copy the write access that opening a mutex needs, and the old catch-all treated that refusal as "nobody is running" - producing two tray icons and a second window whose every row read "Conflict". `Program.IsAnotherInstalledInstanceRunning()` is the belt to that braces: it matches only processes whose executable IS the installed binary (or the dev binary in Dev Mode; a second copy of the INSTALLER is also called "KeyPulse"), and counts any process it cannot inspect as a higher-integrity KeyPulse (skipped in Dev Mode so an elevated production instance never blocks a non-elevated dev run). `EnsureOpenWindowEvent` (`KeyPulse_OpenWindow` / `KeyPulse_OpenWindow_DEV`) uses the same security so "bring the window to the front" works across integrity levels too. Setup mode acquires its session-local `Local\KeyPulse_Setup` (`Local\KeyPulse_Setup_Mutex_v1_DEV` in Dev Mode) lock with a 10,000 ms bounded wait (`TryAcquireSetupLock(10000)`) upfront to prevent race conditions during parent/child installer handoff and concurrent setup collisions. Mutex creation is wrapped in try/catch and never prevents launch. A duplicate launch **signals the running instance to show its window** and exits silently; the Win32 message box is only shown if that signal could not be delivered.
3. **Native Asset Unpacking**: Due to NativeAOT stripping C++ dependencies, `ExtractNativeLibs()` unpacks `libSkiaSharp.dll`, `av_libglesv2.dll`, and `libHarfBuzzSharp.dll` from the assembly's embedded `.dll.gz` resources (GZip-compressed to remove raw uncompressed PE/MZ headers from binary sections while preserving single-file standalone distribution) into `%LOCALAPPDATA%\Programs\KeyPulse\runtime` (`%LOCALAPPDATA%\KeyPulse_DEV\runtime` in Dev Mode) before Avalonia boots. Each file is verified **strictly by actual SHA-256 content hash against the embedded resource**, never solely by length or mutable stamp files. If corrupted or missing, libraries are staged to a `.tmp` file, validated, and atomically moved into place. Stamps serve solely as auxiliary metadata. Insecure or unverified DLL directories are never activated. The folder is inside the install directory on purpose - `%TEMP%` is writable by every other process running as this user, and `SetDllDirectory` points Windows at this verified folder.
4. **Lifecycle Hooks**:
   - If `--uninstall` is passed, it stages itself into `%LOCALAPPDATA%\KeyPulse_Uninstall\KeyPulse_Uninstaller.exe` (avoiding root `%TEMP%` execution flags) and restarts.
   - If `run-ui` is passed (`Program.IsDevMode == true`), the self-installer redirect is bypassed and the app boots directly into the UI inside its isolated Developer Sandbox.
   - If run normally outside of its strict `%LOCALAPPDATA%\Programs\KeyPulse` boundary, it dynamically copies itself to `%LOCALAPPDATA%\KeyPulse_Uninstall` or temporary setup staging and relaunches with `--install-worker` to trigger the installation pipeline (or `--update-worker` during in-app updates to bypass wipe prompts, preserve configurations seamlessly, and auto-restart).
   - `Program.ReleaseSingleInstanceLock()` must be called before ANY `Environment.Exit`. Exit skips finally blocks, so the lock used to be released only by Windows abandoning it at process death, and the replacement instance started only because it caught `AbandonedMutexException`.
5. **Versioning, Updates & Release Architecture**: `build.cmd` synchronizes `version.txt`, `Directory.Build.props`, `KeyPulse.csproj`, and `app.manifest` and stamps `yyyy.MM.dd.HHmm` into the exe via `-p:Version=` (`dev_build.cmd` stamps `0.0.0-dev.<timestamp>` without touching repository version files). `Program.AppVersion` reads it back with `FileVersionInfo` (no reflection, so NativeAOT-safe). Settings shows it and `UpdateChecker` compares versions using complete **SemVer 2.0 precedence rules** (`CompareVersions`, `SplitSemVer`, `ComparePrereleaseIdentifiers`), ensuring stable releases take precedence over corresponding betas (`1.0.0 > 1.0.0-beta`).
   - **Secret-Free Code Signing & Store Support**: CI and release pipelines support automated code signing via Windows Certificate Store thumbprint (`$env:KEYPULSE_CERT_THUMBPRINT`) or certificate paths with environment variable credentials (`$env:KEYPULSE_CERT_PASSWORD`), with zero interactive password prompts.
   - **Cryptographic Asset Integrity & Authenticode**: `UpdateChecker.cs` downloads `SHA256SUMS.txt` if absent in release metadata, strictly validates SHA-256 binary hash, and verifies embedded Authenticode publisher subject via `X509Certificate2.CreateFromSignedFile` (rejecting any binary whose signer is not KeyPulse).
   - **Resumable HTTP Downloads & Backoff**: `UpdateChecker.DownloadUpdateAsync()` supports HTTP `Range: bytes={offset}-` partial downloads and resilient 3-attempt exponential backoff retry.
   - **Background Checks & Notification Retention**: `App.axaml.cs` runs a 24-hour recurring background update check loop and preserves pending notifications (`PendingUpdateResult`) when running hidden in the tray until `MainWindow.BringToFront()` displays them.
   - **Out-of-Process Canary Rollback**: If a newly installed update crashes on boot, `Program.CheckPostUpdateCanaryRecovery()` spawns an out-of-process process swap helper (`cmd.exe /c ping 127.0.0.1 -n 3 & move ... & start ...`) and exits immediately, avoiding in-use Windows executable file lock `IOException`s.
   - **Installer Elevated Process Detection**: `SetupWindow.cs` inspects installed processes and prompts with UAC elevation retry (`--install-worker` / `--update-worker --elevated-retry`) when unkillable elevated processes are detected.
   - **Forward Config Schema Preservation**: `ConfigStore.Save()` uses `Math.Max(config.SchemaVersion, CurrentSchemaVersion)` to prevent downgrading future schema versions.
   - **Forward Backup Compatibility**: `BackupService.ValidatePayload()` skips future unsupported `ActionType` values with user warnings instead of aborting the restore as corrupt.
   - **Atomic Push-After-Verification Pipeline**: `BuildPipeline.ps1` requires a clean git working tree, stages only explicit release files (`$releaseFiles`), and pushes the release commit and tag to `origin` ONLY after remote draft release asset upload and SHA-256 verification succeed, completely preventing orphaned commits on remote.
   - **Dual Changelog Architecture & 5-Release Retention**: Autonomous AI agents and engineers continuously document all granular technical changes, architectural adjustments, and security verifications under `docs/changes.md`. User-facing, consumer-oriented release notes are promoted and curated in `docs/CHANGELOG.md` under `## [Unreleased]`. The release pipeline automatically extracts release notes from `docs/CHANGELOG.md` and retains binary assets for 5 stable and 3 beta releases FIFO while preserving full release history and tags.
6. **Startup Launcher**: If enabled, `Program.SetStartup` writes the startup command directly into HKCU `Software\Microsoft\Windows\CurrentVersion\Run` (`"<ExePath>" --hidden`). Legacy `boot.vbs` script generation and `wscript.exe` execution were completely eliminated to remove heuristic dropper triggers.
7. **Single startup authority**: `Program.IsStartupEnabled()` / `Program.SetStartup()` are the ONLY places that decide startup state. They transparently handle BOTH the `Run` registry key and the elevated `KeyPulse_AdminTask` logon task, so the two launchers can never both fire and elevating/de-elevating cannot silently lose the setting. In Dev Mode (`Program.IsDevMode`), `QueryAdminTaskState()`, `QueryStartupState()`, `SetStartup()`, and `TrySetRegistryStartup()` are strictly isolated no-ops so dev runs never modify Windows startup entries or scheduled tasks.
8. **Elevation & Task Scheduler COM Integration**: `Program.CreateOrUpdateAdminTask`, `EnsureAdminTaskBatterySettings`, and `QueryAdminTaskState` utilize the native Windows `Schedule.Service` COM API (via `ComActivation.cs`) to define, update, and manage the `KeyPulse_AdminTask` directly in memory from XML strings with `<DisallowStartIfOnBatteries>false</DisallowStartIfOnBatteries>`, `<StopIfGoingOnBatteries>false</StopIfGoingOnBatteries>`, and `<StopOnIdleEnd>false</StopOnIdleEnd>`, completely eliminating temporary XML file drops to `%TEMP%` and avoiding unneeded child `schtasks.exe` spawns (with `schtasks.exe` retained solely as a secondary fallback). `MainWindow.VerifyAdminModeIsRealAsync()` runs this check in the background on startup, and `Program.SetStartup` enforces it on startup enablement. `Program.TryRemoveAdminTask` verifies removal and is used by the uninstaller.
9. **Elevation must not lie** (`Program.IsAdminModeClaimedButNotEffective`): the task is created with `/RL HIGHEST`, which on an account without administrator rights simply means ordinary rights - Windows reports the task as enabled while nothing changed. `MainWindow.VerifyAdminModeIsRealAsync()` checks after startup and tells the user plainly; the Settings startup line says the same. The `Privileges` button in Settings dynamically reflects real wired status: Green (`#2e5c46`) when effectively elevated and wired, Amber (`#8a6d1b`, "Elevate To Match Admin Mode") when claimed/wired in Task Scheduler but the running process is unelevated, and Red (`#7d1d1d`) when standard user. `--setup-admin-task` also accepts `--for-user "<account>"`, because a UAC prompt answered with someone else's administrator credentials would otherwise create the logon task for THAT account instead of the person who asked for it.
10. **Start-with-Windows is default-ON and truthful** (ISSUE_33): the admin-task state query is performed via direct COM query (falling back to `schtasks /Query /XML`). `QueryStartupState()` falls through to the `Run` key when the task is merely Disabled - a leftover Run-key launcher still counts as On. `AppConfig.LaunchOnBoot` defaults to true, and on the very first run (config.json did not exist before launch and `!Program.IsDevMode`) `MainWindow` creates the per-user launcher when nothing is enabled, so a clean install genuinely starts with Windows until the user unchecks it. Settings re-asks Windows on every open (`InvalidateAdminTaskState()` first) and shows an indeterminate - never unchecked-looking - square while the state is Unknown.
11. **System Tray, Zero-Padding Icon & Quick Action Menu (`App.axaml.cs` & `KeyPulse.ico`)**: `App.OnFrameworkInitializationCompleted` initializes the main window, builds the system tray menu, and starts `DesktopOrganizerService.EnsureAutoSnapshotScheduler()`.
   - **Zero-Padding Multi-Resolution Icon Architecture (`KeyPulse.ico`)**: To eliminate taskbar crowding and small icon artifacts, `KeyPulse.ico` is compiled with 7 supersampled mipmap resolutions (16x16, 24x24, 32x32, 48x48, 64x64, 128x128, 256x256). All outer transparent padding and internal container padding were eliminated (bounding box `0, 0, width, height` on all sizes). The deep navy squircle badge (`#0f172a`) and electric cyan pulse waveform (`#38bdf8`) with a white-hot inner core span the entire canvas edge-to-edge, ensuring the tray icon renders large, prominent, and razor-sharp on Windows taskbars.
   - **Context Menu Structure**: The tray icon context menu is dynamically maintained by `App.UpdateTrayQuickActions()` in strict top-to-bottom order: `Screen Brightness` submenu at the very top (housing up to 3 pinned brightness presets under a `QUICK ACTIONS` header with an active `✓` indicator, a separator, `Brightness/Contrast Slider`, and `Open Screen Brightness`), followed by a separator, `Desktop Organizer`, followed by a separator, `QUICK ACTIONS` (shortcuts flagged with `AddToQuickActionMenu` that are enabled), followed by a separator and standard controls (`Open KeyPulse`, `Settings`, `Exit KeyPulse`). Clicking a quick action executes the target shortcut without keyboard interaction. Text typing and pasting actions are dispatched with a 180 ms asynchronous delay to allow the context menu to dismiss and restore foreground focus to the active target window before injecting input. Left-clicking tray navigation items (*Screen Brightness*, *Desktop Organizer*, *Settings*) automatically dismisses and hides the main shortcut key bind window behind it (`this.Hide()`).

### Installation & Setup UI (`SetupWindow.cs`)
- An Avalonia `Window` bypassing the main app logic to provide verbose terminal-like logging during lifecycle events.
- **Only the INSTALLED binary is ever closed** (`FindInstalledInstances`): install and uninstall used to force-close every process named "KeyPulse", which a second copy of the installer also is. Two installers launched together killed each other, and a kill landing during the binary copy left a truncated `KeyPulse.exe` behind. A process that cannot be inspected is included on purpose - that is the elevated case ISSUE_5 has to notice.
- **The binary is swapped in, never copied over**: setup writes `KeyPulse.exe.new`, verifies its length against the source, then `File.Move(..., overwrite: true)`. `File.Copy` truncates the destination first, so an interruption used to leave a broken exe where a working one had been.
- **Elevated uninstall retry**: after terminating, the uninstaller re-checks for survivors. If any remain and it is not elevated, it offers to restart itself with `--uninstall --elevated-retry` under UAC (the flag makes the offer un-repeatable). Declining continues and reports the failure with instructions. Without this, uninstalling while Administrator mode was on always failed: the elevated KeyPulse could not be closed, so its file stayed locked and the folder could not be deleted.
- **Setup NEVER writes a whole settings snapshot.** `SaveSetupWindowGeometry()` uses `ConfigStore.TryUpdate` to persist only its own four window values. It used to save the whole in-memory `AppConfig`, which is loaded from disk ONLY inside the upgrade branch - so whenever `config.json` existed but `KeyPulse.exe` did not (folder deleted by hand, exe quarantined, or a roaming `%APPDATA%` reaching a second PC), setup saved a blank config over every shortcut the user had.
- **Pre-Wipe Safe Transaction (CRITICAL)**: When "Wipe Settings" is selected, setup terminates running KeyPulse instances *before* touching configuration to prevent running processes from re-saving state on exit. Before deleting `%APPDATA%\KeyPulse`, `ConfigStore.SaveAllWipeSafetyCopies()` creates safety copies of `config.json`, `desktop_organizer.json`, and `screen_brightness.json` outside the directory (`%APPDATA%\KeyPulse.config.before-wipe-*.json`, `%APPDATA%\KeyPulse.desktop_organizer.before-wipe-*.json`, and `%APPDATA%\KeyPulse.screen_brightness.before-wipe-*.json`). If safety copies cannot be verified, the wipe aborts and alerts the user. The confirmation dialog (`ConfirmWipeAsync`) explicitly discloses the shortcut count, saved desktop layout count, and Screen Brightness preset count.
- **Privilege State Preservation across Upgrades**: When the user chooses "Keep Settings & Upgrade", setup inspects running KeyPulse processes via Win32 token elevation queries (`advapi32.dll!GetTokenInformation` with `TokenElevation`) before terminating them (falling back to checking `GetAdminTaskState() == AdminTaskState.Enabled`). This state is held in `_preserveAdminPrivilege`. During installation (Step 6), if `_preserveAdminPrivilege` was true, setup provisions `KeyPulse_AdminTask` with battery restrictions disabled; if false, it purges the admin task and configures the HKCU `Run` key launcher. Upon completion, "Launch KeyPulse & Close" relaunches `Program.ExePath` with `UseShellExecute = true` and `Verb = "runas"` when `_preserveAdminPrivilege` is true (falling back cleanly to user-level execution if UAC is dismissed), ensuring an administrator instance is seamlessly restored.
- **Non-Intrusive Desktop Shortcut Upgrades**: During application updates or upgrades, Step 5 inspects whether `KeyPulse.lnk` currently exists on the user's Desktop. If found, updates target path and properties; if missing (user previously deleted or cleaned it), creation is skipped entirely (`desktop = null`), preserving the user's clean desktop without generating false-positive warning banners.
- **Non-Elevated Scheduled Task Fast-Path**: Step 6 queries existing task XML and uses `schtasks /Change` to avoid `Access is denied` errors during in-place upgrades preserving administrator privilege.
- **Install Flow**: Cleans legacy temp logs/folders (including `%TEMP%\KeyPulse_NativeLibs` and `%LOCALAPPDATA%\KeyPulse`) -> Scours and deletes any old junk installs from `C:\Program Files` and `C:\Program Files (x86)` -> Sends a graceful `WM_CLOSE` to any running instances (falling back to a brutal `Kill()` only if they hang) -> Provisions `%LOCALAPPDATA%` directory -> Copies binary -> Writes a COMPLETE set of Registry keys for `appwiz.cpl` (`DisplayVersion`, `InstallLocation`, `InstallDate`, `EstimatedSize`, `QuietUninstallString`, `URLInfoAbout`, `HelpLink` - not just a name and an uninstall string) -> Instantly builds Start Menu/Desktop shortcuts using native unmanaged COM VTable function pointers (`ole32!CoCreateInstance` with `IShellLinkW` and `IPersistFile` VTable slots) with an automated PowerShell `WScript.Shell` fallback (skipping desktop shortcut creation if intentionally deleted) -> Purges legacy `boot.vbs` scripts and configures direct HKCU `Run` key or Task Scheduler admin task if startup was previously enabled.
- **Uninstall Flow**: Identical graceful process termination -> **Verified removal of the `KeyPulse_AdminTask` scheduled task** (`Program.TryRemoveAdminTask`, which re-queries the task and reports a manual command if it survives) -> Purges ALL app binaries (including the `runtime` subfolder), the entire `%APPDATA%\KeyPulse` settings folder (config **and** logs), the legacy `%LOCALAPPDATA%\KeyPulse` log folder, legacy `Program Files` debris, `%TEMP%` native lib pollution, registry keys, and shortcuts (invoking `SHChangeNotify(SHCNE_ASSOCCHANGED)` after removing shortcuts and context-menu entries so Windows Explorer refreshes immediately) -> Self-terminates solely through `SetupWindow_Closing`'s 30-cycle retry loop targeting self-deletion and directory removal (no competing background `cmd.exe` processes spawned from UI buttons). Registry startup keys are cleanly accessed via deterministic `using` scopes.

### Configuration & State UI (`MainWindow.axaml` & `.cs`)
- **Dynamic Multi-Hotkey Capture**: The hotkey editor supports zero, one, or multiple keyboard combinations per action. Key combinations are managed via the `KeyCombo` box and `AddKeyButton` ("+ Add Key"), rendered as removable chips in `ComboChipsPanel`.
- **Zero-Hotkey Manual Actions**: Actions can have zero combinations, displaying `Ready (Manual)` status with purple styling. These actions can be triggered directly using the row `[Run]` button or added to the Tray Quick Action menu (`⚡`) for one-click manual firing.
- **Optional Action Display Name**: `HotkeyEntry.DisplayName` allows user-facing labeling (e.g. "Work Email Signature"), taking visual precedence in `ActionTitle` over raw action descriptors while preserving the underlying action type and target.
- **Validation**: When text changes, it calls `HotkeyManager.Probe()` to ensure the key isn't claimed by the OS (colors Red if conflicting). On conflict, `HotkeyManager.SuggestAlternative()` probes nearby combinations and offers a free one.
- **Search & Sort**: The `ListBox` binds to `VisibleHotkeys`, a filtered/sorted projection of the master `Hotkeys` collection. `RefreshVisibleHotkeys()` must be called after ANY mutation of `Hotkeys`. Matches search against `DisplayName`, `Target`, and all combinations.
- **Registration resilience**: `ApplyHotkeys()` validates only the *shape* of a target (`ValidateTargetShape`). Reachability (`IsTargetAvailableNow`) only sets a `Waiting` status; it never unregisters. A 30-second `DispatcherTimer` retries `Waiting`/`Conflict` rows so they self-heal. Reachability checks in `QueueAvailabilityCheck` are de-duplicated via `_activeAvailabilityChecks` to prevent unbounded task accumulation on `_availabilityGate`.
- **Incremental registration (CRITICAL)**: `ApplyHotkeys()` **reconciles**, it does not rebuild. For each action, it reconciles the set of `KeyCombinations` against `RegisteredHotkeyIds`, registering new combos and unregistering removed ones individually without touching unaffected combinations. Individual combination health is tracked in `ComboStatuses` and `ComboHints`, yielding `Ready`, `Partial`, `Conflict`, or `Ready (Manual)`. It must NEVER call `HotkeyManager.Clear()`: doing so released every hotkey the user owned on every add, edit, toggle, removal and 30-second retry, and any press landing in that gap was silently lost. `Clear()` is for shutdown only. A row leaving the list must have `ReleaseRegistration` called on it before removal.
- **Conflict suggestions are cached**: `SuggestAlternative` costs up to sixteen blocking register/unregister round trips. `HotkeyEntry.SuggestedForCombo` stops the retry timer recomputing it every 30 seconds forever.
- **Backup / Restore**: owned entirely by `BackupService.cs`. See its own section below.
- **Theme & Dev Sandbox Window Title**: `App.ApplyTheme()` applies `AppConfig.Theme` (System / Light / Dark). `App.axaml` no longer pins `RequestedThemeVariant`. When `Program.IsDevMode` is true, `MainWindow` sets its title to `"KeyPulse [DEV SANDBOX]"` for unambiguous visual distinction, and the Settings `Check for Updates` action supports launching local installer binaries (`result.LocalInstallerPath`) when `KEYPULSE_DEV_UPDATE_SOURCE` is active (`DEVUPDATE_01`).
- **Hidden targets**: the list binds `TargetDisplay` and `TargetTooltip`, NEVER `Target`. When `IsTargetObfuscated` is set the row renders a mask under a radius-12 blur, the tool tip says "Hidden", and `MatchesSearch` skips the value. Binding `Target` there - with the secret also sitting in the tool tip - meant one second of hovering, or one search, defeated the whole feature.
- **Quick Action Configuration & Tab Navigation**: `ActionCombo` binds `SelectionChanged="ActionCombo_SelectionChanged"` (including launch, URL, folder, and text actions; Screen Brightness hotkeys are managed directly within the dedicated Screen Brightness window) and `TargetText` binds `TextChanged="TargetText_TextChanged"`. Standardized `TargetText.MinHeight = 34` prevents sudden height jumping/stutter when selecting text actions, and the editor card column 2 is constrained to star (`*`) with `TextWrapping.Wrap` enabled across all target types to prevent massive URLs/scripts from blowing out the window horizontally. Row 4 of the shortcut editor features an `Add to Quick Action Menu` checkbox (`QuickActionCheck`) beside `ObfuscateCheck`. TabIndex flows logically across all controls: `KeyCombo (0), AddKeyButton (1), ActionCombo (2), ActionNameText (3), TargetText (4), ObfuscateCheck (5), QuickActionCheck (6), ExpandTargetBtn (7), BrowseBtn (8), AddButton (9), CancelEditButton (10), SearchBox (11), Shortcut Headers (12..15), and Bottom Bar Actions (16..18)`. Shortcuts marked for quick action display a `⚡` badge next to their key combination in the list. Deleting an entry that is currently being edited calls `ClearRowEditingExcept(null)` before cancelling edit state so no stale `IsEditing` flag survives. The bottom bar provides `Screen Brightness`, `Desktop Organizer`, and `Settings` buttons.
- **Consolidated 4-Tab Categorized Settings Architecture (`MainWindow.axaml.cs`)**: The Settings modal dialog organizes all app configurations into 4 top-tier application groupings:
  1. **General**: Startup at Windows boot, tray integration, live administrator privileges state with 1-click elevation/reversion microcopy ("Run as Admin", "Revert to User"), startup admin mismatch banner with direct "Restart As Administrator" button, typing delay with inline speed validation (1–200 ms), preferred web browser selection (System Default, Chrome, Edge, Firefox, Brave) with real-time detection and fallback, and sound effects.
  2. **Appearance**: Visual color theme selection (Match Windows, Light mode, Dark mode) with WCAG AA compliant theme-aware contrast.
  3. **Displays & Icons**: Screen Brightness shortcuts/settings integration, Desktop Organizer automation (auto-restore icon positions on display change, auto-periodic snapshot backup scheduler), and display synchronization options.
  4. **Backup & Updates**: Application update checks, configurable update channels (Stable vs Beta) with conditional dropdown dimming when auto-check is disabled, configuration backup export (with optional AES-256-GCM encryption and `👁` password reveal toggle), backup restoration, and an isolated red Danger Zone factory reset.
  - **Physical Property Sheet Ear Styling & Window Lifecycle**: Tabs are rendered as top-rounded ears (`CornerRadius = 6, 6, 0, 0`) physically connected to the content page container (`pageContainer`). The active tab has zero bottom border (`BorderThickness = 1, 1, 1, 0`) and overlaps the top border of `pageContainer` by 1px with matching background (`AppPanelRaisedBrush`), creating a continuous surface identical to top-tier Windows property sheets. Inactive tabs have recessed backgrounds, subtle borders, and smooth hover/keyboard transitions. Features a single-instance guard (`_activeSettingsWindow`), modal ownership (`ShowDialogOrWindowAsync` with owner `w`), persistent window state/geometry memory (`SettingsWindowState`, `SettingsWindowX`, `SettingsWindowY`, `SettingsWindowWidth`, `SettingsWindowHeight`), a live instant search bar filtering dynamically across all settings, and contextual per-tab and global "Restore Defaults" actions with confirmation guards.
  - **Resilient Theme-Variant Brush Resolution (`AppBrush`)**: `MainWindow.AppBrush` queries `app.TryGetResource(resourceKey, app.ActualThemeVariant, out var res)` with deterministic dark/light solid brush fallbacks (and global fallback brushes in `<Application.Resources>`), guaranteeing that inactive tabs, panels, and borders never resolve to transparent brushes even when `ThemeDictionaries` lookups fail.
- **Shortcut Search Filter**: Features a left-aligned `"Search:"` label, a compact `TextBox` with constrained geometry (`MinWidth="250"`, `MaxWidth="350"`), and an embedded right-aligned `"✕"` button to immediately clear the filter.
- **Top-Tier Interactive Scroll Overflow Indicators & Navigation**: When shortcuts exceed the viewport, an interactive floating pill indicator `ScrollMoreDownPill` (`[ ▼ X more shortcuts below ▼ ]`) dynamically calculates offscreen items and smoothly pages down on click; when scrolled down, `ScrollMoreUpPill` (`[ ▲ Back to top ▲ ]`) provides immediate jump-to-top navigation. `ScrollFadeBottom` / `ScrollFadeTop` cast a theme elevation glow (`#401d4ed8` in dark mode), and the vertical scrollbar is explicitly styled (`Width="10"`, `AllowAutoHide="False"`, high-contrast thumb) so overflow is immediately obvious upon launch.
- **The shortcut table (`ShortcutHeaderGrid` + the ListBox item template)**: the header and the rows
  are two SEPARATE grids whose `ColumnDefinitions` lists must be kept identical. Column order is
  `0 Status, 1 sep, 2 Shortcut, 3 sep, 4 Action, 5 sep, 6 Target, 7 sep, 8 Actions`. Every resizable
  column binds to its own `{DynamicResource}`; the Actions column is a FIXED
  `ShortcutActionsColumnWidth` (310 = three buttons: Run, Edit, Delete + spacing) and
  must never be `Auto` - with two separate grids, `Auto` measured the word "Actions" in the header
  and the buttons in the rows, so the heading did not sit over its own column. Column 8 in both the
  header grid and the row item template is explicitly framed with `BorderThickness="0,0,1,1"` to terminate
  the table cleanly. Table headers support full WCAG AA keyboard accessibility with `Focusable="True"`,
  `TabIndex="12".."15"`, and `ShortcutHeader_KeyDown` for Tab cycling, Space/Enter sorting, and Left/Right navigation. Each splitter resizes
  the two columns it physically sits between, and `CaptureShortcutColumnWidths` reads indices
  0/2/4/6 into their matching settings.
- **Key names**: `HotkeyManager` owns the ONLY key-name table (`CanonicalKeyNames` / `KeyNameAliases`). `MainWindow.MapAvaloniaKeyToVirtualKey` is the single bridge from Avalonia's `Key` enum. Never write `Key.ToString()` into the shortcut box: `Add` (the keypad plus) used to parse as `0xBB`, the `=` key, so the shortcut the user tested was not the one that got registered.
- **No static event may outlive the window**: `_rawKeyHandler` holds the `HotkeyManager.OnRawKey` subscription so `OnClosed` can detach it. `HotkeyManager` is static, so a lambda left subscribed there keeps the window and its whole visual tree alive for the life of the process.
- **Every launched process is released**: each `Process.Start` result is wrapped in `using`. "Open folder" and "Launch program" fire on every shortcut press, so discarding the handle accumulated them between collections.
- **Non-activating notices**: `ShowActionMessage` and the typing-progress window set `ShowActivated = false` and never call `Activate()`. A shortcut failing mid-sentence must not pull the keyboard out of the app the user is typing in.
- **Elevation restarts & Wired Privilege State**: `RelaunchWithPrivilegeChange` saves BEFORE starting the elevated process and only exits if that process actually started. The old code called `Environment.Exit(0)` unconditionally, which skipped `OnClosing` and lost every unsaved edit - including when the user declined the UAC prompt. The Settings `Privileges` button dynamically reflects real wired status asynchronously (`LoadStartupStateAsync`): Green (`#2e5c46`) when effectively elevated and wired, Amber (`#8a6d1b`, "Elevate To Match Admin Mode") when claimed in Task Scheduler but running unelevated (offering a choice to restart elevated or revert Task Scheduler to user level), and Red (`#7d1d1d`) when standard user.
- **schtasks is a process**: `Program.GetAdminTaskState()` caches its answer and `Program.InvalidateAdminTaskState()` must be called after every `/Create`, `/Change` or `/Delete`. Settings loads the startup state on a background task. Never query it synchronously on the UI thread.
- **The main window opens through `MainWindow.BringToFront()` only** (ISSUE_32): a `--hidden` boot never calls `Show()`, so `Opened` fires for the FIRST time exactly when the user clicks the tray - often hours or days later. The old unconditional `if (_startHidden) Hide();` inside `MainWindow_Opened` turned that first open into a half-second flash (window appears, `Opened` hides it again); the Settings window was unaffected because it is a fresh window each time. `BringToFront()` sets `_userAskedToBeShown` BEFORE `Show()`, and only a Show nobody asked for may still be re-hidden. The show/hide/close lifecycle is logged to the debug log so window problems can finally be diagnosed from `%APPDATA%\KeyPulse\logs\keypulse_debug.txt`.

### Hotkey Interception (`HotKeyManager.cs`)
- **Background Win32 Loop**: Spawns a dedicated background thread utilizing `CreateWindowEx(HWND_MESSAGE)` to construct a hidden Win32 message-only window.
- **Native Intercepts**: Uses `RegisterHotKey` and `UnregisterHotKey`. Traps `WM_HOTKEY` events globally across the OS, translating the integer ID back into a C# `Action` callback.
- **`RunOnThread` owns its signal, the caller does not**: the `ManualResetEventSlim` is disposed by the queued task, not by a `using` in the waiter. A timed-out wait used to dispose it while the task was still queued, so `Set()` threw into the message loop's empty catch and the work completed silently AFTER the caller had reported failure - leaving the status column disagreeing with what Windows had actually done.
- **Probe Functionality**: Dynamically checks combinations against an internal `_activeCombos` tracker. If KeyPulse already owns the hotkey, it successfully greenlights it. Otherwise, it tests OS-level availability by registering/unregistering a dummy ID.
- **Capture Hook (CRITICAL)**: `HookCallback` swallows keystrokes ONLY while `IsCaptureMode` **AND** a KeyPulse window is the foreground window (`IsKeyPulseForeground()`). Without that second condition the hook ate the entire machine's keyboard whenever the shortcut box held focus. `MainWindow` additionally disables the hook on `Deactivated`. Never remove either guard.

### Automation Engine (`InputSimulator.cs`)
- Handles execution of user actions.
- **Win32 `SendInput`**: Injects real hardware **scan codes** (`KEYEVENTF_SCANCODE` with `wVk = 0`) for the `TypeText` action, in batches. Virtual-key-only injection was invisible to games, RDP sessions and VMs, so the shortcut appeared to do nothing at all. Every injected event carries `InputSimulator.InjectionTag` in `dwExtraInfo` so the capture hook can recognise and ignore KeyPulse's own output.
- **Keyboard layout (CRITICAL)**: `GetTargetKeyboardLayout()` asks the FOREGROUND window's thread which layout it uses. `GetKeyboardLayout(0)` answers for KeyPulse's own thread and produced scrambled text whenever the target app was on a different layout. Never go back to `GetKeyboardLayout(0)`.
- **Typing speed**: `InputSimulator.CharacterDelayMs` mirrors `AppConfig.TypingDelayMs` (Fast 1 / Normal 6 / Compatible 18 ms) and characters are sent in batches. The old fixed 12 ms sleep after every character locked the keyboard for over half a minute on a 3,000-character snippet, with no setting to change it. Runs are single-flight (`IsTyping` gate), cancellable (Esc or `CancelTyping()`), and raise `TypingStarted` / `TypingProgressChanged` / `TypingFinished` so the UI can show a non-activating progress window.
- **Clipboard backup has a TOTAL budget**, not just a per-format one: `ClipboardBackupBudgetBytes` (96 MB) on top of `ClipboardSingleFormatLimitBytes` (64 MB). One large image is offered by Windows in several formats at once, so a per-format-only limit let a single paste copy hundreds of megabytes aside, all of it on the Large Object Heap, on every press. Anything over budget is reported through the existing `warning` out-parameter.
- **Clipboard Owner HWND & Sequence Safety**: All `OpenClipboard` calls pass a valid Win32 message-only window handle (`_clipboardOwnerHwnd`). Before restoring backed-up clipboard content after paste simulation, `GetClipboardSequenceNumber()` is checked; if another application placed new content on the clipboard during injection, restore is aborted to prevent clobbering user data.
- **Clipboard Injection**: `InsertText` enumerates clipboard formats but only backs up **HGLOBAL (moveable memory) formats**. GDI-handle formats (`CF_BITMAP`, `CF_PALETTE`, `CF_METAFILEPICT`, `CF_ENHMETAFILE`, the `CF_GDIOBJ*` range) are NOT memory blocks; byte-copying them destroyed the user's clipboard. They are skipped and reported to the user via the `warning` out-parameter. `CF_DIB`, `CF_DIBV5` and `CF_HDROP` ARE memory and survive intact.
- **Paste timing**: after `Ctrl+V`, `WaitForClipboardToBeConsumed(2000)` polls `GetOpenClipboardWindow()` until a foreign process has opened and closed the clipboard (2.0 s cap) before restoring. The previous fixed 500 ms sleep pasted stale content on slow/remote targets.
- Avalonia's built-in clipboard is purposefully abandoned to prevent `Dispatcher.UIThread` deadlocks.

### Backup & Restore (`BackupService.cs`)
Everything that can refuse, warn or roll back lives in `BackupService` so the UI cannot skip a check.
The rule it exists to enforce: **a file replaces the user's shortcuts only after it has proved what it
is, proved it is undamaged, and been read end to end.** Nothing is touched before all three hold.

- **File format v2**: a readable `BackupEnvelope` (FileType, FormatVersion, CreatedUtc,
  CreatedByVersion, Encryption, KDF parameters, `PayloadSha256`) wrapping a base64 `BackupPayload`.
  The envelope stays readable on purpose so the file can identify itself, be dated, and be recognised
  as encrypted BEFORE anyone is asked for a passphrase.
- **Encryption at rest (optional, offered on every export)**: AES-256-GCM, key from
  PBKDF2-SHA256 with a random 16-byte salt and 300,000 iterations, 12-byte nonce, 16-byte tag,
  AAD `"KeyPulseBackup.v2"`. Both the derivation and the write run on a background thread. There is
  no recovery path for a forgotten passphrase and the UI says so.
- **Integrity**: `PayloadSha256` is checked BEFORE the payload is parsed, so a bit-flip or a
  truncation can never reach the shortcut list. `Write` also reads the finished file back and
  re-decrypts it - a backup that cannot be read again is not a backup.
- **Atomic write**: through `AtomicFileWriter.WriteAtomic` with fallback protection.
- **What travels**: every shortcut (including `DisplayName`, `KeyCombinations`, `IsTargetObfuscated`, `AddToQuickActionMenu`),
  the complete Desktop Organizer configuration and profiles (`BackupPayload.DesktopOrganizer`),
  the complete Screen Brightness configuration, hardware bindings, lock states, and presets (`BackupPayload.ScreenBrightness`),
  the browser/sound/theme/typing-speed/sort preferences, `HasSeenTrayHint`, and the full window
  layout - main, Settings and Setup geometry plus all four column widths.
- **What deliberately does NOT travel**: `AppConfig.LaunchOnBoot`. Whether KeyPulse starts with
  Windows is a property of the machine (a registry value or a scheduled task), and silently turning
  it on because a backup from another PC had it on would be an unpleasant surprise. Restore says so.
- **Targets are exported in plain form inside the payload**, on purpose: on disk they are DPAPI-bound
  to this Windows account (see below), so a protected copy could never be restored anywhere else -
  which is the one case backups exist for. Protection for the FILE is the passphrase.
- **Geometry is validated against the CURRENT machine** (`ApplyRestoredWindowLayout`): sizes are
  clamped to the working area, a position is used only when it lands on a monitor that is actually
  attached, and `Minimized` is never restored. A position from a three-monitor desk would otherwise
  open the window somewhere the user cannot reach, which looks exactly like the app failing to start.
- **Corruption vs. machine differences**: `ValidatePayload` refuses the WHOLE file for structural
  damage (an action code outside `ActionType`, a null row, a failed checksum) and imports-and-flags
  anything that is merely different about this PC (keys already taken, a missing folder, a
  combination this build cannot parse). Rejecting a file for the second kind is what made restore
  useless on a new PC.
- **Backwards compatibility**: every backup taken by an earlier build is a raw copy of `config.json`.
  `Inspect` recognises those, decrypts their legacy `ENC:` targets, and upgrades them. The guard that
  keeps this from reopening the old data-loss hole is a `JsonDocument` shape check: a `"Hotkeys"`
  array must be PRESENT IN THE FILE. A deserializer's default empty list is never good enough.
- **Rollback**: `ConfigStore.SaveAllRollbackCopies("before-restore")` writes timestamped rollback copies of all active stores (`config.json`, `desktop_organizer.json`, and `screen_brightness.json`) before a restore replaces them. Any exception during import restores all snapshots; if the rollback itself fails, the message reports the backup paths to recover by hand.

### Desktop Organizer (`DesktopOrganizerService.cs` & `DesktopOrganizerWindow.axaml.cs`)
- **Multi-Monitor Layout Management**: Captures and restores desktop icon coordinates across single and multi-display setups. Layout profiles are persisted to `%APPDATA%\KeyPulse\desktop_organizer.json`. Cross-monitor proportional scaling runs whenever saved monitor bounds are present (`profile.Monitors.Count > 0`), even if the current monitor count differs from when the profile was saved. Features 4 customizable placement options for unsaved new icons: Center of primary screen (Default), Untouched in place, Align down right side, and Center of secondary monitor.
- **Atomic Persistence, LKG Redundancy & Empty-Overwrite Guard**: `SaveConfig` utilizes `AtomicFileWriter.WriteAtomic`, copies the existing valid `desktop_organizer.json` to `desktop_organizer.lkg.json` before overwriting, and updates `desktop_organizer.lkg.json` after each verified write. `DesktopOrganizerWindow` sets `_suppressConfigEvents = true` before `InitializeComponent()` (and omits static `SelectedIndex` in XAML) so initial control construction cannot trigger a premature save before `LoadConfig()` completes. Furthermore, `SaveConfig(config, allowEmptyProfiles)` refuses to overwrite a non-empty on-disk profile list with an empty in-memory list unless `allowEmptyProfiles: true` is explicitly passed from the user's `Delete` action.
- **Inline Profile Renaming & Non-Overlapping Profile Cards**: Each profile card uses a `WrapPanel` with clipping constraints so badges (`MANUAL (Protected)` vs. `AUTO-SNAPSHOT (x/5)`, `ACTIVE`) wrap fluidly without overflowing into column 1 or overlapping `Restore Layout` buttons. Inline renaming activates a dedicated rename editor row with explicit `[Save]` and `[Cancel]` buttons (in addition to `Enter`/`Escape` keybindings) so users never feel trapped.
- **Configurable Periodic Auto-Snapshots**: When `AutoPeriodicSnapshotEnabled` is checked, `EnsureAutoSnapshotScheduler()` runs an initial check (after a 15-second startup delay) and a 6-hour background timer to capture automated snapshots on a customizable day interval (`AutoSnapshotIntervalDays`, `1–30 days`, default 3 days) with an interactive stepper (`− / +`). Auto-snapshots skip execution if fewer monitors are connected than previously seen or if no icon moved by more than 4 pixels compared to the newest snapshot, and automatically prune only the oldest auto-snapshot beyond `MaxAutoSnapshots = 5` while **never** auto-deleting user-created manual profiles.
- **Corrupt Profile Quarantine & Graceful Recovery**: Load failures return a typed `DesktopOrganizerLoadResult` without erasing in-memory profiles. If `desktop_organizer.json` is corrupted, it is quarantined to `desktop_organizer.damaged-<timestamp>.json` and automatic recovery from the LKG backup is attempted. If recovery fails, the UI enters Read-Only mode to protect surviving profile state from accidental overwrite.
- **Pre-Wipe Safety Preservation**: Desktop Organizer profiles are included in the setup wipe safety system via `ConfigStore.SaveAllWipeSafetyCopies()` and backup envelopes.
- **Auto-Arrange Guard**: `RestoreLayout` verifies `IsAutoArrangeActive(out bool desktopVisible)` upfront, warning the user and aborting restoration if Windows Auto-Arrange is enabled.
- **Boundary Clamping**: Anti-collision icon coordinate displacement contains horizontal boundary checks (`maxX` and `minCurX` wrap/clamp) to prevent icon displacement beyond visible monitor coordinates.
- **Shell COM Desktop Interop (Zero Memory Injection)**: Icon position queries and desktop layout restoration communicate natively via Windows Shell COM interfaces (`IShellWindows`, `IServiceProvider`, `IShellBrowser`, `IShellView`, and `IFolderView` `cde725b0-ccc9-4519-917e-325d72fab4ce`), completely eliminating cross-process memory allocation (`VirtualAllocEx`), remote process memory reading (`ReadProcessMemory`), and hooking heuristics.
- **Theme Awareness & Audio Feedback**: Resource brushes resolve dynamically against `app.ActualThemeVariant` within `ThemeDictionaries`. Interactive feedback relies strictly on embedded assembly assets (`click.wav`).

### Screen Brightness & Contrast Control (`ScreenBrightnessService.cs`, `ScreenBrightnessOverlayWindow.cs`, `ScreenBrightnessWindow.cs`)
- **Movable, Resizable & Geometry-Remembering Brightness/Contrast Slider**: The tray overlay window (`ScreenBrightnessOverlayWindow`), titled **Brightness/Contrast Slider**, is fully resizable (`CanResize = true`) and movable by dragging the title bar (`BeginMoveDrag`). Its screen position and dimensions (`OverlayWindowX`, `OverlayWindowY`, `OverlayWindowWidth`, `OverlayWindowHeight`) are automatically remembered in `ScreenBrightnessConfig`. Disconnected monitors are dynamically hidden and the window scales responsively without numeric clipping or slider collisions.
- **Master Stepper Action Buttons (`−` and `+`)**: Replaced confusing `−5%` and `+5%` text with clean, bold, high-contrast `−` and `+` square buttons (32x30 footprint, bold 16pt font, hand cursor, pressed indentation) for immediate one-click stepping across all displays.
- **Linked "All Displays (Synced)" Master Slider with Boundary Clamping Memory (Fixed Gap)**:
  - Features prominent gradient styling (`#162032` to `#1e1b4b`), vibrant border (`#38BDF8` to `#818CF8`), and `SYNCED MASTER` badge.
  - Implements virtual boundary tracking (`VirtualBrightness` and `VirtualContrast`, clamp range `[-100, 200]`).
  - Preserves custom differential gap offsets across 2, 3, or more displays. When dragged down to 0% or up to 100%, physical monitors clamp safely at hardware boundaries without controller damage. When moving back in reverse direction, monitors unclamp in exact reverse order, restoring original custom gaps.
  - Adjusting any individual monitor slider calls `ReanchorAllScreens()`, locking in the new differential baseline for subsequent master adjustments.
  - Pointer capture drag session tracking (`_isUserDraggingMaster`) prevents background hardware state reads from interrupting or resetting the slider thumb mid-drag.
- **Custom Monitor Nicknames Everywhere**: When a user assigns a friendly nickname (e.g. *Samsung 4K*), it displays directly across slider card headers (hiding redundant slot badges), preset editor tables, direct hotkey dropdowns, and identify screen flash banners, falling back to *Screen A*, *Screen B*, *Screen C* only when no nickname is configured.
- **Dual Vertical Sliders & Lock Ratio**: Each active screen container houses two vertical sliders (`0–100`): left for **Brightness**, right for **Contrast**, with bold live numeric readouts directly above each slider, Mouse Wheel (`±2`) and Up/Down Arrow support, and a per-screen **Lock Ratio** checkbox underneath (governed globally by the default-ON **Lock Brightness & Contrast Together Tight** setting). When locked, moving either slider moves the other to the exact same value immediately; re-checking **Lock Ratio** immediately snaps Contrast to match Brightness's current value.
- **Hardware DDC/CI & NativeAOT Laptop Backlight Control**: External monitors are controlled via `dxva2.dll` (`GetNumberOfPhysicalMonitorsFromHMONITOR`, `GetPhysicalMonitorsFromHMONITOR`, `GetMonitorBrightness`, `SetMonitorBrightness`, `GetMonitorContrast`, `SetMonitorContrast`) with low-level Win32 `SetVCPFeature` (opcode `0x10` for Luminance, `0x12` for Contrast) and `GetVCPFeatureAndVCPFeatureReply` integrated as automatic fallbacks when high-level MCCS calls fail. Contrast write failures are decoupled from brightness operations so secondary contrast failures never invalidate or revert successful brightness writes. Every physical monitor handle is guaranteed to be released via `DestroyPhysicalMonitors` inside a `finally` block. Internal laptop displays are controlled via NativeAOT-safe Win32 `\\.\LCD` kernel `DeviceIoControl` (`IOCTL_VIDEO_QUERY_SUPPORTED_BRIGHTNESS`, `IOCTL_VIDEO_QUERY_DISPLAY_BRIGHTNESS`, `IOCTL_VIDEO_SET_DISPLAY_BRIGHTNESS`) bound strictly to primary display Slot 0. Hardware `Min..Max` ranges are normalized to a `0–100%` percentage scale with no artificial minimum floor (`0%` maps to hardware `Min`).
- **Sequential Multi-Display Execution & GPU I2C Multiplexer Protection (CRITICAL)**: Multi-display updates (`ApplyProfileToHardwareDeltaOnly`) are executed sequentially across connected displays in a single `foreach` loop over deterministically sorted slot indices (`bound.Keys.OrderBy(k => k)`). Parallel execution (`Parallel.ForEach`) is strictly prohibited because concurrent DDC/CI calls trigger race conditions on the GPU's display controller I2C bus multiplexer, causing bus collisions, packet drops, or driver hangs. A mandatory 30 ms settling delay (`Thread.Sleep(30)`) is enforced between distinct physical displays, with cancellation token checks (`token.IsCancellationRequested`) at every iteration.
- **VESA MCCS Inter-Command Pause for Dual-Writes & Write Retry Loop (CRITICAL)**: Per the VESA Monitor Control Command Set (MCCS) standard, monitor scaler microcontrollers require internal processing time after receiving a command before accepting subsequent commands. When writing both Brightness and Contrast to a physical DDC/CI monitor in `TryWriteDdcMonitor`, a mandatory pause of 40 ms (`Thread.Sleep(40)`) MUST be inserted immediately after `SetMonitorBrightness` completes and before `SetMonitorContrast` begins. Direct writes execute without redundant pre-write I2C reads, backed by a 3-attempt retry loop with 35 ms settling sleep to eliminate I2C bus lockups and slider freezes when running alongside third-party monitor utilities (e.g. Twinkle Tray).
- **Hardware Range Clamping & Software Bounds Sanitization**: Raw values sent to `SetMonitorBrightness` and `SetMonitorContrast` are strictly clamped to the physical monitor's capabilities: `raw = Math.Clamp(raw, min, max)` where `min` and `max` are reported by `GetMonitorBrightness` and `GetMonitorContrast`. Software inputs are strictly clamped to `[0, 100]` while allowing 0% (which maps to the monitor's minimum hardware level) without arbitrary cutoffs.
- **250 ms Hardware Speed Limiter, Trailing-Edge Flush & Delta-Only Writes**: Slider movements are throttled per screen to at most one hardware write every `250 ms` (`RequestScreenLevelChange` / `QueueThrottledHardwareWrite`), with a guaranteed trailing-edge flush (`ExecutePendingWriteForSlot`) when the 250 ms window ends so the physical monitor always receives the final number. Hardware writes skip any screen whose target Brightness and Contrast match its last applied hardware values (delta-only writes) to prevent backlight flicker and unnecessary I2C bus traffic.
- **Decoupled Disk Persistence (Zero Disk Thrashing on Slider Drag)**: `RequestScreenLevelChange` only updates in-memory configuration (`slotCfg.LastBrightness`, `slotCfg.LastContrast`) and avoids synchronous disk writes (`SaveConfigInternal`). Disk persistence is deferred exclusively to the background trailing-edge flush in `ExecutePendingWriteForSlot` (`Task.Run(() => { lock (ConfigLock) SaveConfigInternal(cfg); })`) once slider interaction settles. Deterministic persistence on window close is guaranteed by `ScreenBrightnessService.FlushConfig()` in `Closing`/`Closed` handlers in `ScreenBrightnessWindow.cs` and `CloseSafe`/`OnOverlayClosed` in `ScreenBrightnessOverlayWindow.cs`.
- **Non-Blocking Serialized Live Read & User-Touch Priority**: Opening the sliders renders cached values in `0 ms` (`GetImmediateCachedStates`) and queries physical monitors sequentially on background threads with a 35 ms inter-monitor pause (`ReadAllScreensLiveAsync`), preventing GPU I2C multiplexer bus contention. Touching, dragging, or scrolling a screen's slider sets a per-screen user-touch flag (`ScreenContainerView.UserTouched = true`) that cancels/ignores the initial background read for that screen so late hardware replies never jump the slider back.
- **Dedicated Screen Brightness Shortcuts, Bidirectional Cycling & Granular Display Targeting**: Brightness shortcuts are managed directly in the Screen Brightness window (`ScreenBrightnessService.RegisterBrightnessHotkeys`). Global `CycleUpHotkey` and `CycleDownHotkey` step forward or backward through presets marked `IncludeInCycle` (up to 10 presets) without OSD popups or focus changes. Global `StepUpHotkey` and `StepDownHotkey` default to dual number-row and numpad bindings (`"Ctrl+Alt+=, Ctrl+Alt+NumPadAdd"` and `"Ctrl+Alt+-, Ctrl+Alt+NumPadSubtract"`), adjusting brightness across all displays in ±5% deltas (`StepDelta`). An intelligent **Multi-Monitor Differential Lock** (`LockMonitorDifferential`, default ON) preserves relative display offsets while naturally compressing at boundary limits (0% floor, 100% ceiling), falling back to cursor-focused display stepping when unlocked. Both overlay and main window feature a linked **All Displays Master Slider** with ±5% steppers. Users can configure dedicated **Instant Screen Level Hotkeys** (`ScreenDirectHotkey`, e.g. `Ctrl+Alt+1` -> Screen A to 70%) for specific monitors or all displays. Interactive hotkey recording engages low-level keyboard capture (`HotkeyManager.EnableCaptureHook()`) on focus to prevent Windows from consuming shortcuts as active actions during assignment, with automatic cross-action collision clearing. Each preset supports an individual direct hotkey (`Hotkey`), plus per-screen enable checkboxes (`ScreenCycleEntry.Enabled`) allowing users to target single monitors (e.g., brighten Display A only while leaving Display B untouched). Unconditional blind writes and VCP opcodes (`0x10`/`0x12`) provide fail-safe DDC/CI write fallback. Redundant no-op steps continue to be filtered against active connected displays.

### Interop, Persistence & Utilities (`Models.cs`, `ConfigStore.cs`, `CryptoHelper.cs`, `AtomicFileWriter.cs`, `IpcService.cs`, `ComActivation.cs`)
- State is managed via the `AppConfig` class, stored at `%APPDATA%\KeyPulse\config.json`, alongside `DesktopOrganizerConfig` (`%APPDATA%\KeyPulse\desktop_organizer.json` / `.lkg.json`) and `ScreenBrightnessConfig` (`%APPDATA%\KeyPulse\screen_brightness.json` / `.lkg.json`). When `Program.IsDevMode` is true (`DEVDATA_01`), `ConfigStore.ConfigDirectory` (and `ScreenBrightnessService.AppDataFolder`) routes all configuration, Desktop Organizer layouts, and Screen Brightness presets to `KEYPULSE_DEV_DATA_DIR` / `%LOCALAPPDATA%\KeyPulse_DEV\data` (with clean-baseline snapshots persisted in `%LOCALAPPDATA%\KeyPulse_DEV\keep`), guaranteeing zero cross-contamination with `%APPDATA%\KeyPulse`. When running inside test runners (`testhost`, `vstest`), `ConfigStore.ConfigDirectory` auto-detects the test execution environment and isolates to `%TEMP%\KeyPulse_Test_Sandbox`. Pre-overwrite backups (`config.backup-<timestamp>.json`), retention pruning (newest 10), dedicated safety copies (`config.safety-shortcuts.json`), and LKG empty-overwrite protection safeguard user shortcuts against unintended wipes.
- **NativeAOT COM Interop, Shortcut Creation & Activation (`ComActivation.cs` & `SetupWindow.cs`)**: NativeAOT-safe COM object creation using Win32 `ole32!CoCreateInstance` (`CreateInstance<T>`) for Shell COM (`IShellWindows`, `IFolderView`) and Task Scheduler 2.0 (`ITaskService`). Avoids reflection and CLR coclass constructor instantiation (`new Coclass()`), preventing NativeAOT `ILC` metadata errors while ensuring deterministic COM cleanup. For Windows Shell Shortcut (`.lnk`) creation in `SetupWindow.cs`, invokes unmanaged COM VTable function pointers (`delegate* unmanaged[Stdcall]`) for `IShellLinkW` and `IPersistFile` with zero CLR dynamic RCW generation, backed by an autonomous PowerShell `WScript.Shell` fallback.
- **Target protection**: `CryptoHelper` uses **DPAPI (`ProtectedData`, CurrentUser scope)** with a fixed entropy string and writes a `DPAPI:` prefix. The old `ENC:` AES format, whose key and IV were hard-coded in the executable, is still READ for migration and never written again. `TryUnprotect` returns **false** on failure and the row is flagged `TargetUnreadable`; it must NEVER return the cipher text, which is how a shortcut's target silently became the literal string `ENC:8Kd2...`. `TargetProtectionFailed` is strictly scoped to `CryptoHelper.ProtectionUnavailable && IsTargetObfuscated`, guaranteeing that ordinary non-secret targets (URLs, script paths) never trigger false DPAPI security alerts.
- **`ConfigStore` is the ONLY reader/writer of that file.** It writes atomically through `AtomicFileWriter.WriteAtomic`, and on a damaged/unreadable file it **renames the file aside** as `config.damaged-<timestamp>.json` and reports the problem. Nothing in this codebase may `File.Delete` or blind-overwrite the config: doing so is how every shortcut used to vanish silently.
- **Atomic File Writing (`AtomicFileWriter`)**: Shared atomic writer utility employing `.tmp` staging, multi-attempt Win32 `File.Replace` with backup, and atomic `File.Move(overwrite: true)` fallback. Never falls back to non-atomic `File.Copy`.
- **Named Pipe IPC (`IpcService`)**: Low-integrity SDDL (`D:(A;;GA;;;WD)S:(ML;;NW;;;LW)`) Named Pipe server/client (`KeyPulse_IPC_Session_<SessionId>`, or `KeyPulse_IPC_DEV_Session_<SessionId>` in Dev Mode) for shell context-menu "Add to KeyPulse" requests, providing length-prefixed framing and synchronous acknowledgment without file-based collision races.
- Holds an array of `HotkeyEntry` objects (DisplayName, KeyCombinations, ActionType, Target string, `IsTargetObfuscated`, `AddToQuickActionMenu`) alongside UI bounds, desktop organizer profile configurations, and screen brightness configurations.
- **Serialization Constraint**: As the app is `NativeAOT`, reflection-based JSON serialization is forbidden. `JsonSerializerContext` source generators (`AppConfigJsonContext`) are strictly enforced. All floating-point numbers support named literals (`AllowNamedFloatingPointLiterals`).

### CRITICAL HARDWARE PROTECTION & I2C/DDC BUS GUARD RAILS (MANDATORY DISCLAIMER)
> [!CAUTION]
> **MANDATORY HARDWARE PROTECTION PROTOCOL (FOR ALL AI AGENTS & DEVELOPERS):**
> The Screen Brightness subsystem interfaces directly with physical monitor scaler microcontrollers over the GPU I2C bus (DDC/CI via `dxva2.dll`) and laptop backlight hardware (`\\.\LCD`). Hardware microcontrollers (MCUs) run on low-speed embedded clock cycles and have zero tolerance for race conditions or packet floods. Any regression of the following guard rails can cause physical monitor MCU lockups, EEPROM/scaler register corruption, backlight flickering, display driver crashes, or SSD disk thrashing. These constraints are NOT performance suggestions; they are mandatory safety invariants:
>
> 1. **SEQUENTIAL MULTI-DISPLAY WRITES ONLY (`Parallel.ForEach` IS STRICTLY FORBIDDEN)**:
>    Multi-monitor profile applications (`ApplyProfileToHardwareDeltaOnly`) MUST run sequentially in a single `foreach` loop over deterministically sorted slot indices (`bound.Keys.OrderBy(k => k)`). The GPU's display controller I2C bus multiplexer CANNOT service concurrent transactions across distinct physical ports simultaneously. Concurrent writes trigger hardware bus collisions and driver deadlocks.
>
> 2. **MANDATORY 30 MS INTER-DISPLAY SETTLING DELAY**:
>    Between distinct physical display writes in `ApplyProfileToHardwareDeltaOnly`, a delay of `Thread.Sleep(30)` MUST be enforced. This allows the GPU display multiplexer and I2C lines to settle between physical addresses. Every iteration must check `token.IsCancellationRequested` before and after the sleep.
>
> 3. **MANDATORY 40 MS VESA MCCS DUAL-WRITE PAUSE & DIRECT WRITE RETRY LOOP**:
>    Under the VESA Monitor Control Command Set (MCCS) standard, monitor scalers require internal processing recovery time between sequential commands. When issuing dual writes (`writeBrightness` AND `writeContrast` are both true in `TryWriteDdcMonitor`), a mandatory pause of `Thread.Sleep(40)` MUST be inserted immediately after `SetMonitorBrightness` completes and before `SetMonitorContrast` begins. Direct writes execute without redundant pre-write I2C reads, backed by a 3-attempt retry loop with 35 ms settling sleep to eliminate I2C bus lockups and slider freezes when running alongside third-party monitor utilities (e.g. Twinkle Tray).
>
> 4. **STRICT HARDWARE RAW CLAMPING & ZERO-FLOOR PRESERVATION**:
>    Hardware raw values passed to `SetMonitorBrightness` and `SetMonitorContrast` MUST be clamped strictly within the physical limits returned by the monitor: `Math.Clamp(raw, dwMinimum, dwMaximum)`. Software inputs must clamp within `[0, 100]` while allowing 0% (mapped to `dwMinimum`) without arbitrary software floors.
>
> 5. **PER-SCREEN 250 MS HARDWARE SPEED LIMITER & TRAILING-EDGE FLUSH**:
>    Slider adjustments MUST be throttled to at most one write per 250 ms (`ScreenWriteThrottle.ThrottleIntervalMs = 250`) via `QueueThrottledHardwareWrite`. When slider motion ceases, `ExecutePendingWriteForSlot` MUST perform a trailing-edge flush to guarantee the user's final selected value reaches hardware.
>
> 6. **DECOUPLED DISK PERSISTENCE (ZERO DISK THRASHING ON SLIDER DRAG)**:
>    Synchronous disk writes (`SaveConfigInternal`) inside real-time slider drag handlers (`RequestScreenLevelChange`) are STRICTLY FORBIDDEN. Moving a slider must ONLY mutate in-memory state (`slotCfg.LastBrightness`, `slotCfg.LastContrast`). Disk writes occur exclusively in the background trailing-edge flush in `ExecutePendingWriteForSlot` (`Task.Run`) once motion settles, and deterministically on window closure via `ScreenBrightnessService.FlushConfig()`.
>
> 7. **DELTA-ONLY HARDWARE FILTERING**:
>    Never dispatch writes to hardware if `targetB == prevB && targetC == prevC`. Skipping unchanged values prevents backlight pulsing and unnecessary I2C bus traffic.
>
> 8. **DETERMINISTIC MONITOR HANDLE DESTRUCTION**:
>    Every handle returned by `GetPhysicalMonitorsFromHMONITOR` MUST be freed via `DestroyPhysicalMonitors` in a `finally` block to prevent GDI/kernel handle leaks that exhaust OS-wide DDC/CI resources.
- **NEVER restore clipboard without checking `GetClipboardSequenceNumber()`.** If external content was copied during text injection, skip restore.

- **The app manifest declares PerMonitorV2 DPI awareness.** Do not remove it; the UI becomes bitmap-stretched and blurry.
- **NEVER create or update `KeyPulse_AdminTask` without stripping battery constraints (`DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` set to `false`).** Windows Task Scheduler defaults to disallowing execution on battery power, breaking autostart on laptops.
