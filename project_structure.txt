================================================================================
# KEYPULSE - ARCHITECTURE AND SOURCE OF TRUTH (CONTEXT FILE)
================================================================================

## 1. PROJECT OVERVIEW
**KeyPulse** is a lightning-fast, ultra-lightweight Windows hotkey manager designed for power users. 
- **Tech Stack**: C# 13, .NET 9, Avalonia UI 12.1.
- **Compilation**: Single-file `NativeAOT` (No .NET runtime dependencies).
- **OS Target**: Windows x64 Strictly (Heavily relies on Win32 P/Invoke).

## 2. CORE ARCHITECTURE & LOGIC FLOW

### Boot / Initialization (`Program.cs` & `App.axaml.cs`)
1. Executable is launched. `Program.cs` intercepts the startup arguments. Passing `run-ui` or setting `KEYPULSE_DEV_MODE=1` activates `Program.IsDevMode` (`DEVDATA_01`), running the application in a strictly isolated Developer Sandbox (`%LOCALAPPDATA%\KeyPulse_DEV`) with zero cross-contamination against the installed production app.
2. **Mutex Protection**: Checks a **session-local** `Local\KeyPulse_SingleInstance_Mutex_v1` mutex (`Local\KeyPulse_SingleInstance_Mutex_v1_DEV` in Dev Mode), created through `CreateSharedMutex` with the SDDL `D:(A;;GA;;;WD)S:(ML;;NW;;;LW)`. The **low mandatory label is load-bearing**: an object created by the elevated logon-task instance otherwise carries a High label, Windows refuses a normal-integrity copy the write access that opening a mutex needs, and the old catch-all treated that refusal as "nobody is running" - producing two tray icons and a second window whose every row read "Conflict". `Program.IsAnotherInstalledInstanceRunning()` is the belt to that braces: it matches only processes whose executable IS the installed binary (or the dev binary in Dev Mode; a second copy of the INSTALLER is also called "KeyPulse"), and counts any process it cannot inspect as a higher-integrity KeyPulse (skipped in Dev Mode so an elevated production instance never blocks a non-elevated dev run). `EnsureOpenWindowEvent` (`KeyPulse_OpenWindow` / `KeyPulse_OpenWindow_DEV`) uses the same security so "bring the window to the front" works across integrity levels too. Setup mode acquires its session-local `Local\KeyPulse_Setup` (`Local\KeyPulse_Setup_Mutex_v1_DEV` in Dev Mode) lock with a 10,000 ms bounded wait (`TryAcquireSetupLock(10000)`) upfront to prevent race conditions during parent/child installer handoff and concurrent setup collisions. Mutex creation is wrapped in try/catch and never prevents launch. A duplicate launch **signals the running instance to show its window** and exits silently; the Win32 message box is only shown if that signal could not be delivered.
3. **Native Asset Unpacking**: Due to NativeAOT stripping C++ dependencies, `ExtractNativeLibs()` unpacks `libSkiaSharp.dll`, `av_libglesv2.dll`, and `libHarfBuzzSharp.dll` from the assembly's embedded resources into `%LOCALAPPDATA%\Programs\KeyPulse\runtime` (`%LOCALAPPDATA%\KeyPulse_DEV\runtime` in Dev Mode) before Avalonia boots. Each file is verified **strictly by actual SHA-256 content hash against the embedded resource**, never solely by length or mutable stamp files. If corrupted or missing, libraries are staged to a `.tmp` file, validated, and atomically moved into place. Stamps serve solely as auxiliary metadata. Insecure or unverified DLL directories are never activated. The folder is inside the install directory on purpose - `%TEMP%` is writable by every other process running as this user, and `SetDllDirectory` points Windows at this verified folder.
4. **Lifecycle Hooks**:
   - If `--uninstall` is passed, it copies itself to `%TEMP%\KeyPulse_Uninstaller.exe` and restarts.
   - If `run-ui` is passed (`Program.IsDevMode == true`), the self-installer redirect is bypassed and the app boots directly into the UI inside its isolated Developer Sandbox.
   - If run normally outside of its strict `%LOCALAPPDATA%\Programs\KeyPulse` boundary, it dynamically copies itself to `%TEMP%` and relaunches with `--install-worker` to trigger the installation pipeline.
   - The uninstall bootstrap copy is wrapped in try/catch and reports failure with a message box. Unguarded, a full `%TEMP%` killed the process with no window at all, and Add/Remove Programs looked like a dead button.
   - `Program.ReleaseSingleInstanceLock()` must be called before ANY `Environment.Exit`. Exit skips finally blocks, so the lock used to be released only by Windows abandoning it at process death, and the replacement instance started only because it caught `AbandonedMutexException`.
5. **Versioning & Updates**: `build.cmd` synchronizes `version.txt`, `Directory.Build.props`, `KeyPulse.csproj`, and `app.manifest` and stamps `yyyy.MM.dd.HHmm` into the exe via `-p:Version=` (`dev_build.cmd` stamps `0.0.0-dev.<timestamp>` without touching repository version files). `Program.AppVersion` reads it back with `FileVersionInfo` (no reflection, so NativeAOT-safe). Settings shows it and `UpdateChecker` compares it against the GitHub releases API on demand, stripping prerelease suffixes (`-`) and build metadata (`+`) before numeric token comparisons. When `KEYPULSE_DEV_UPDATE_SOURCE` is set by `.\dev.cmd` (`DEVUPDATE_01`), `UpdateChecker` inspects the local `.\compiled\KeyPulse.exe` produced by `.\dev_build.cmd` instead of querying GitHub so update flows can be tested offline before release.
6. **Startup Launcher**: If enabled, `Program.SetStartup` writes a minimal `boot.vbs` that launches KeyPulse **once** and exits. The old WMI 60-second watchdog loop was removed: it resurrected the app after a deliberate user Exit.
7. **Single startup authority**: `Program.IsStartupEnabled()` / `Program.SetStartup()` are the ONLY places that decide startup state. They transparently handle BOTH the `Run` registry key and the elevated `KeyPulse_AdminTask` logon task, so the two launchers can never both fire and elevating/de-elevating cannot silently lose the setting. In Dev Mode (`Program.IsDevMode`), `QueryAdminTaskState()`, `QueryStartupState()`, `SetStartup()`, and `TrySetRegistryStartup()` are strictly isolated no-ops so dev runs never modify Windows startup entries or scheduled tasks.
8. **Elevation & Task XML Battery Stripping**: `--setup-admin-task` and `--remove-admin-task` check the `schtasks` exit code and verify the resulting task state. When created via standard `schtasks /Create /SC ONLOGON`, Windows defaults `<DisallowStartIfOnBatteries>true</DisallowStartIfOnBatteries>` and `<StopIfGoingOnBatteries>true</StopIfGoingOnBatteries>`, which prevents the app from starting on laptops running on battery. `Program.CreateOrUpdateAdminTask` builds the full task XML with `<DisallowStartIfOnBatteries>false</DisallowStartIfOnBatteries>`, `<StopIfGoingOnBatteries>false</StopIfGoingOnBatteries>`, `<StopOnIdleEnd>false</StopOnIdleEnd>`, and registers it with `schtasks /Create /XML <tempXml> /F` (omitting `/RU` so Windows uses the InteractiveToken without prompting for a user password on stdin and hanging). `Program.EnsureAdminTaskBatterySettings()` queries existing task XML and dynamically patches battery settings if they ever revert. `MainWindow.VerifyAdminModeIsRealAsync()` runs this check in the background on startup, and `Program.SetStartup` enforces it on startup enablement. `Program.TryRemoveAdminTask` verifies removal and is used by the uninstaller.
9. **Elevation must not lie** (`Program.IsAdminModeClaimedButNotEffective`): the task is created with `/RL HIGHEST`, which on an account without administrator rights simply means ordinary rights - Windows reports the task as enabled while nothing changed. `MainWindow.VerifyAdminModeIsRealAsync()` checks after startup and tells the user plainly; the Settings startup line says the same. The `Privileges` button in Settings dynamically reflects real wired status: Green (`#2e5c46`) when effectively elevated and wired, Amber (`#8a6d1b`, "Elevate To Match Admin Mode") when claimed/wired in Task Scheduler but the running process is unelevated, and Red (`#7d1d1d`) when standard user. `--setup-admin-task` also accepts `--for-user "<account>"`, because a UAC prompt answered with someone else's administrator credentials would otherwise create the logon task for THAT account instead of the person who asked for it.
10. **Start-with-Windows is default-ON and truthful** (ISSUE_33): the admin-task state query is a plain `schtasks /Query /XML` (an earlier stray `ONELINE` token made every query fail with "Improper display format type specified", which surfaced as `AdminTaskState.Unknown`, froze the Settings checkbox behind "Windows did not answer..." and let the checkbox and reality disagree forever while the task kept launching KeyPulse at logon). `QueryStartupState()` falls through to the `Run` key when the task is merely Disabled - a leftover Run-key launcher still counts as On. `AppConfig.LaunchOnBoot` defaults to true, and on the very first run (config.json did not exist before launch and `!Program.IsDevMode`) `MainWindow` creates the per-user launcher when nothing is enabled, so a clean install genuinely starts with Windows until the user unchecks it. Settings re-asks Windows on every open (`InvalidateAdminTaskState()` first) and shows an indeterminate - never unchecked-looking - square while the state is Unknown.
11. **System Tray & Quick Action Menu (`App.axaml.cs`)**: `App.OnFrameworkInitializationCompleted` initializes the main window, builds the system tray menu, and starts `DesktopOrganizerService.EnsureAutoSnapshotScheduler()`. The tray icon context menu is dynamically maintained by `App.UpdateTrayQuickActions()` in strict top-to-bottom order: `Screen Brightness` submenu at the very top (housing up to 3 pinned brightness presets under a `QUICK ACTIONS` header with an active `✓` indicator, a separator, `Quick Sliders (Overlay)`, and `Open Screen Brightness`), followed by a separator, `Desktop Organizer`, followed by a separator, `QUICK ACTIONS` (shortcuts flagged with `AddToQuickActionMenu` that are enabled), followed by a separator and standard controls (`Open KeyPulse`, `Settings`, `Exit KeyPulse`). Clicking a quick action executes the target shortcut without keyboard interaction. Text typing and pasting actions are dispatched with a 180 ms asynchronous delay to allow the context menu to dismiss and restore foreground focus to the active target window before injecting input.

### Installation & Setup UI (`SetupWindow.cs`)
- An Avalonia `Window` bypassing the main app logic to provide verbose terminal-like logging during lifecycle events.
- **Only the INSTALLED binary is ever closed** (`FindInstalledInstances`): install and uninstall used to force-close every process named "KeyPulse", which a second copy of the installer also is. Two installers launched together killed each other, and a kill landing during the binary copy left a truncated `KeyPulse.exe` behind. A process that cannot be inspected is included on purpose - that is the elevated case ISSUE_5 has to notice.
- **The binary is swapped in, never copied over**: setup writes `KeyPulse.exe.new`, verifies its length against the source, then `File.Move(..., overwrite: true)`. `File.Copy` truncates the destination first, so an interruption used to leave a broken exe where a working one had been.
- **Elevated uninstall retry**: after terminating, the uninstaller re-checks for survivors. If any remain and it is not elevated, it offers to restart itself with `--uninstall --elevated-retry` under UAC (the flag makes the offer un-repeatable). Declining continues and reports the failure with instructions. Without this, uninstalling while Administrator mode was on always failed: the elevated KeyPulse could not be closed, so its file stayed locked and the folder could not be deleted.
- **Setup NEVER writes a whole settings snapshot.** `SaveSetupWindowGeometry()` uses `ConfigStore.TryUpdate` to persist only its own four window values. It used to save the whole in-memory `AppConfig`, which is loaded from disk ONLY inside the upgrade branch - so whenever `config.json` existed but `KeyPulse.exe` did not (folder deleted by hand, exe quarantined, or a roaming `%APPDATA%` reaching a second PC), setup saved a blank config over every shortcut the user had.
- **Pre-Wipe Safe Transaction (CRITICAL)**: When "Wipe Settings" is selected, setup terminates running KeyPulse instances *before* touching configuration to prevent running processes from re-saving state on exit. Before deleting `%APPDATA%\KeyPulse`, `ConfigStore.SaveAllWipeSafetyCopies()` creates safety copies of `config.json`, `desktop_organizer.json`, and `screen_brightness.json` outside the directory (`%APPDATA%\KeyPulse.config.before-wipe-*.json`, `%APPDATA%\KeyPulse.desktop_organizer.before-wipe-*.json`, and `%APPDATA%\KeyPulse.screen_brightness.before-wipe-*.json`). If safety copies cannot be verified, the wipe aborts and alerts the user. The confirmation dialog (`ConfirmWipeAsync`) explicitly discloses the shortcut count, saved desktop layout count, and Screen Brightness preset count.
- **Privilege State Preservation across Upgrades**: When the user chooses "Keep Settings & Upgrade", setup inspects running KeyPulse processes via Win32 token elevation queries (`advapi32.dll!GetTokenInformation` with `TokenElevation`) before terminating them (falling back to checking `GetAdminTaskState() == AdminTaskState.Enabled`). This state is held in `_preserveAdminPrivilege`. During installation (Step 6), if `_preserveAdminPrivilege` was true, setup provisions `KeyPulse_AdminTask` with battery restrictions disabled; if false, it purges the admin task and configures the HKCU `Run` key launcher. Upon completion, "Launch KeyPulse & Close" relaunches `Program.ExePath` with `UseShellExecute = true` and `Verb = "runas"` when `_preserveAdminPrivilege` is true (falling back cleanly to user-level execution if UAC is dismissed), ensuring an administrator instance is seamlessly restored.
- **Install Flow**: Cleans legacy temp logs/folders (including `%TEMP%\KeyPulse_NativeLibs` and `%LOCALAPPDATA%\KeyPulse`) -> Scours and deletes any old junk installs from `C:\Program Files` and `C:\Program Files (x86)` -> Sends a graceful `WM_CLOSE` to any running instances (falling back to a brutal `Kill()` only if they hang) -> Provisions `%LOCALAPPDATA%` directory -> Copies binary -> Writes a COMPLETE set of Registry keys for `appwiz.cpl` (`DisplayVersion`, `InstallLocation`, `InstallDate`, `EstimatedSize`, `QuietUninstallString`, `URLInfoAbout`, `HelpLink` - not just a name and an uninstall string) -> Instantly builds Start Menu/Desktop shortcuts using native C# COM Interop (`IShellLink`) -> Upgrades `boot.vbs` syntax if startup was previously enabled.
- **Uninstall Flow**: Identical graceful process termination -> **Verified removal of the `KeyPulse_AdminTask` scheduled task** (`Program.TryRemoveAdminTask`, which re-queries the task and reports a manual command if it survives) -> Purges ALL app binaries (including the `runtime` subfolder), the entire `%APPDATA%\KeyPulse` settings folder (config **and** logs), the legacy `%LOCALAPPDATA%\KeyPulse` log folder, legacy `Program Files` debris, `%TEMP%` native lib pollution, registry keys, and shortcuts (invoking `SHChangeNotify(SHCNE_ASSOCCHANGED)` after removing shortcuts and context-menu entries so Windows Explorer refreshes immediately) -> Self-terminates solely through `SetupWindow_Closing`'s 30-cycle retry loop targeting self-deletion and directory removal (no competing background `cmd.exe` processes spawned from UI buttons). Registry startup keys are cleanly accessed via deterministic `using` scopes.

### Configuration & State UI (`MainWindow.axaml` & `.cs`)
- **Dynamic Multi-Hotkey Capture**: The hotkey editor supports zero, one, or multiple keyboard combinations per action. Key combinations are managed via the `KeyCombo` box and `AddKeyButton` ("+ Add Key"), rendered as removable chips in `ComboChipsPanel`.
- **Zero-Hotkey Manual Actions**: Actions can have zero combinations, displaying `Ready (Manual)` status with purple styling. These actions can be triggered directly using the row `[RUN]` button or added to the Tray Quick Action menu (`⚡`) for one-click manual firing.
- **Optional Action Display Name**: `HotkeyEntry.DisplayName` allows user-facing labeling (e.g. "Work Email Signature"), taking visual precedence in `ActionTitle` over raw action descriptors while preserving the underlying action type and target.
- **Validation**: When text changes, it calls `HotkeyManager.Probe()` to ensure the key isn't claimed by the OS (colors Red if conflicting). On conflict, `HotkeyManager.SuggestAlternative()` probes nearby combinations and offers a free one.
- **Search & Sort**: The `ListBox` binds to `VisibleHotkeys`, a filtered/sorted projection of the master `Hotkeys` collection. `RefreshVisibleHotkeys()` must be called after ANY mutation of `Hotkeys`. Matches search against `DisplayName`, `Target`, and all combinations.
- **Registration resilience**: `ApplyHotkeys()` validates only the *shape* of a target (`ValidateTargetShape`). Reachability (`IsTargetAvailableNow`) only sets a `Waiting` status; it never unregisters. A 30-second `DispatcherTimer` retries `Waiting`/`Conflict` rows so they self-heal. Reachability checks in `QueueAvailabilityCheck` are de-duplicated via `_activeAvailabilityChecks` to prevent unbounded task accumulation on `_availabilityGate`.
- **Incremental registration (CRITICAL)**: `ApplyHotkeys()` **reconciles**, it does not rebuild. For each action, it reconciles the set of `KeyCombinations` against `RegisteredHotkeyIds`, registering new combos and unregistering removed ones individually without touching unaffected combinations. Individual combination health is tracked in `ComboStatuses` and `ComboHints`, yielding `Ready`, `Partial`, `Conflict`, or `Ready (Manual)`. It must NEVER call `HotkeyManager.Clear()`: doing so released every hotkey the user owned on every add, edit, toggle, removal and 30-second retry, and any press landing in that gap was silently lost. `Clear()` is for shutdown only. A row leaving the list must have `ReleaseRegistration` called on it before removal.
- **Conflict suggestions are cached**: `SuggestAlternative` costs up to sixteen blocking register/unregister round trips. `HotkeyEntry.SuggestedForCombo` stops the retry timer recomputing it every 30 seconds forever.
- **Backup / Restore**: owned entirely by `BackupService.cs`. See its own section below.
- **Theme & Dev Sandbox Window Title**: `App.ApplyTheme()` applies `AppConfig.Theme` (System / Light / Dark). `App.axaml` no longer pins `RequestedThemeVariant`. When `Program.IsDevMode` is true, `MainWindow` sets its title to `"KeyPulse [DEV SANDBOX]"` for unambiguous visual distinction, and the Settings `Check for Updates` action supports launching local installer binaries (`result.LocalInstallerPath`) when `KEYPULSE_DEV_UPDATE_SOURCE` is active (`DEVUPDATE_01`).
- **Hidden targets**: the list binds `TargetDisplay` and `TargetTooltip`, NEVER `Target`. When `IsTargetObfuscated` is set the row renders a mask under a radius-12 blur, the tool tip says "Hidden", and `MatchesSearch` skips the value. Binding `Target` there - with the secret also sitting in the tool tip - meant one second of hovering, or one search, defeated the whole feature.
- **Quick Action Configuration & Tab Navigation**: `ActionCombo` binds `SelectionChanged="ActionCombo_SelectionChanged"` (including `Cycle screen brightness` / `ActionType.CycleBrightness` alongside launch/URL/folder/text actions; when `CycleBrightness` is selected, `TargetText` is hidden and pre-filled with `"Cycle configured brightness presets"`, while `ConfigurePresetsBtn` opens the Screen Brightness preset editor) and `TargetText` binds `TextChanged="TargetText_TextChanged"`. Row 4 of the shortcut editor features an `Add to Quick Action Menu` checkbox (`QuickActionCheck`) beside `ObfuscateCheck`. TabIndex flows left-to-right: `TargetText (2), ObfuscateCheck (3), QuickActionCheck (4), ExpandTargetBtn (5), BrowseBtn (6), AddButton (7), CancelEditButton (8), SearchBox (9)`. Shortcuts marked for quick action display a `⚡` badge next to their key combination in the list. Deleting an entry that is currently being edited calls `ClearRowEditingExcept(null)` before cancelling edit state so no stale `IsEditing` flag survives. The bottom bar provides `Screen Brightness`, `Desktop Organizer`, and `Settings` buttons.
- **Consolidated 4-Tab Settings Dialog Architecture (`SettingsDialog.axaml.cs`)**: The Settings modal dialog organizes all app configurations into 4 logical top-level tabs:
  1. **General**: Startup at logon, minimize to tray, start minimized, single-click tray toggle, notification sounds, and sound pack selection.
  2. **Typing & Speed**: Scan-code typing simulation speed with a custom millisecond delay stepper (`1–200 ms`, enabled conditionally only when Custom is chosen), and global clipboard backup/restore budget settings.
  3. **Window & Display**: Color theme selection (System / Dark / Light), physical monitor brightness & contrast lock, and direct navigation buttons to open Desktop Organizer and Screen Brightness.
  4. **Advanced & Safety**: Update checking, administrator privileges query & restart, encrypted backup & restore, full per-tab and global "Restore Defaults" options, and an isolated red Danger Zone for factory resets with confirmation dialogs.
  The Settings dialog includes an instant live search bar filtering across all tabs (>15 settings), remembers window position and last active tab (`LastActiveSettingsTab`), supports full keyboard navigation (`Tab` flow, `Enter` to commit, `Esc` to close), and enforces non-technical human-friendly microcopy with verbose descriptive tooltips (`?` icons).
- **The shortcut table (`ShortcutHeaderGrid` + the ListBox item template)**: the header and the rows
  are two SEPARATE grids whose `ColumnDefinitions` lists must be kept identical. Column order is
  `0 Status, 1 sep, 2 Shortcut, 3 sep, 4 Action, 5 sep, 6 Target, 7 sep, 8 Actions`. Every resizable
  column binds to its own `{DynamicResource}`; the Actions column is a FIXED
  `ShortcutActionsColumnWidth` (310 = three buttons: Run, Edit, Delete + spacing) and
  must never be `Auto` - with two separate grids, `Auto` measured the word "Actions" in the header
  and the buttons in the rows, so the heading did not sit over its own column. Each splitter resizes
  the two columns it physically sits between, and `CaptureShortcutColumnWidths` reads indices
  0/2/4/6 into their matching settings.
- **Key names**: `HotkeyManager` owns the ONLY key-name table (`CanonicalKeyNames` / `KeyNameAliases`). `MainWindow.MapAvaloniaKeyToVirtualKey` is the single bridge from Avalonia's `Key` enum. Never write `Key.ToString()` into the shortcut box: `Add` (the keypad plus) used to parse as `0xBB`, the `=` key, so the shortcut the user tested was not the one that got registered.
- **No static event may outlive the window**: `_rawKeyHandler` holds the `HotkeyManager.OnRawKey` subscription so `OnClosed` can detach it. `HotkeyManager` is static, so a lambda left subscribed there keeps the window and its whole visual tree alive for the life of the process.
- **Every launched process is released**: each `Process.Start` result is wrapped in `using`. "Open folder" and "Launch program" fire on every shortcut press, so discarding the handle accumulated them between collections.
- **Non-activating notices**: `ShowActionMessage` and the typing-progress window set `ShowActivated = false` and never call `Activate()`. A shortcut failing mid-sentence must not pull the keyboard out of the app the user is typing in.
- **Elevation restarts & Wired Privilege State**: `RelaunchWithPrivilegeChange` saves BEFORE starting the elevated process and only exits if that process actually started. The old code called `Environment.Exit(0)` unconditionally, which skipped `OnClosing` and lost every unsaved edit - including when the user declined the UAC prompt. The Settings `Privileges` button dynamically reflects real wired status asynchronously (`LoadStartupStateAsync`): Green (`#2e5c46`) when effectively elevated and wired, Amber (`#8a6d1b`, "Elevate To Match Admin Mode") when claimed in Task Scheduler but running unelevated (offering a choice to restart elevated or revert Task Scheduler to user level), and Red (`#7d1d1d`) when standard user.
- **schtasks is a process**: `Program.GetAdminTaskState()` caches its answer and `Program.InvalidateAdminTaskState()` must be called after every `/Create`, `/Change` or `/Delete`. Settings loads the startup state on a background task. Never query it synchronously on the UI thread.
- **The main window opens through `MainWindow.BringToFront()` only** (ISSUE_32): a `--hidden` boot never calls `Show()`, so `Opened` fires for the FIRST time exactly when the user clicks the tray - often hours or days later. The old unconditional `if (_startHidden) Hide();` inside `MainWindow_Opened` turned that first open into a half-second flash (window appears, `Opened` hides it again); the Settings window was unaffected because it is a fresh window each time. `BringToFront()` sets `_userAskedToBeShown` BEFORE `Show()`, and only a Show nobody asked for may still be re-hidden. The show/hide/close lifecycle is logged to the debug log so window problems can finally be diagnosed from `%APPDATA%\KeyPulse\logs\keypulse_debug.txt`.

### Hotkey Interception (`HotKeyManager.cs`)
- **Background Win32 Loop**: Spawns a dedicated background thread utilizing `CreateWindowEx(HWND_MESSAGE)` to construct a hidden Win32 message-only window.
- **Native Intercepts**: Uses `RegisterHotKey` and `UnregisterHotKey`. Traps `WM_HOTKEY` events globally across the OS, translating the integer ID back into a C# `Action` callback.
- **`RunOnThread` owns its signal, the caller does not**: the `ManualResetEventSlim` is disposed by the queued task, not by a `using` in the waiter. A timed-out wait used to dispose it while the task was still queued, so `Set()` threw into the message loop's empty catch and the work completed silently AFTER the caller had reported failure - leaving the status column disagreeing with what Windows had actually done.
- **Probe Functionality**: Dynamically checks combinations against an internal `_activeCombos` tracker. If KeyPulse already owns the hotkey, it successfully greenlights it. Otherwise, it tests OS-level availability by registering/unregistering a dummy ID.
- **Capture Hook (CRITICAL)**: `HookCallback` swallows keystrokes ONLY while `IsCaptureMode` **AND** a KeyPulse window is the foreground window (`IsKeyPulseForeground()`). Without that second condition the hook ate the entire machine's keyboard whenever the shortcut box held focus. `MainWindow` additionally disables the hook on `Deactivated`. Never remove either guard.

### Automation Engine (`InputSimulator.cs`)
- Handles execution of user actions.
- **Win32 `SendInput`**: Injects real hardware **scan codes** (`KEYEVENTF_SCANCODE` with `wVk = 0`) for the `TypeText` action, in batches. Virtual-key-only injection was invisible to games, RDP sessions and VMs, so the shortcut appeared to do nothing at all. Every injected event carries `InputSimulator.InjectionTag` in `dwExtraInfo` so the capture hook can recognise and ignore KeyPulse's own output.
- **Keyboard layout (CRITICAL)**: `GetTargetKeyboardLayout()` asks the FOREGROUND window's thread which layout it uses. `GetKeyboardLayout(0)` answers for KeyPulse's own thread and produced scrambled text whenever the target app was on a different layout. Never go back to `GetKeyboardLayout(0)`.
- **Typing speed**: `InputSimulator.CharacterDelayMs` mirrors `AppConfig.TypingDelayMs` (Fast 1 / Normal 6 / Compatible 18 ms) and characters are sent in batches. The old fixed 12 ms sleep after every character locked the keyboard for over half a minute on a 3,000-character snippet, with no setting to change it. Runs are single-flight (`IsTyping` gate), cancellable (Esc or `CancelTyping()`), and raise `TypingStarted` / `TypingProgressChanged` / `TypingFinished` so the UI can show a non-activating progress window.
- **Clipboard backup has a TOTAL budget**, not just a per-format one: `ClipboardBackupBudgetBytes` (96 MB) on top of `ClipboardSingleFormatLimitBytes` (64 MB). One large image is offered by Windows in several formats at once, so a per-format-only limit let a single paste copy hundreds of megabytes aside, all of it on the Large Object Heap, on every press. Anything over budget is reported through the existing `warning` out-parameter.
- **Clipboard Owner HWND & Sequence Safety**: All `OpenClipboard` calls pass a valid Win32 message-only window handle (`_clipboardOwnerHwnd`). Before restoring backed-up clipboard content after paste simulation, `GetClipboardSequenceNumber()` is checked; if another application placed new content on the clipboard during injection, restore is aborted to prevent clobbering user data.
- **Clipboard Injection**: `InsertText` enumerates clipboard formats but only backs up **HGLOBAL (moveable memory) formats**. GDI-handle formats (`CF_BITMAP`, `CF_PALETTE`, `CF_METAFILEPICT`, `CF_ENHMETAFILE`, the `CF_GDIOBJ*` range) are NOT memory blocks; byte-copying them destroyed the user's clipboard. They are skipped and reported to the user via the `warning` out-parameter. `CF_DIB`, `CF_DIBV5` and `CF_HDROP` ARE memory and survive intact.
- **Paste timing**: after `Ctrl+V`, `WaitForClipboardToBeConsumed(2000)` polls `GetOpenClipboardWindow()` until a foreign process has opened and closed the clipboard (2.0 s cap) before restoring. The previous fixed 500 ms sleep pasted stale content on slow/remote targets.
- Avalonia's built-in clipboard is purposefully abandoned to prevent `Dispatcher.UIThread` deadlocks.

### Backup & Restore (`BackupService.cs`)
Everything that can refuse, warn or roll back lives in `BackupService` so the UI cannot skip a check.
The rule it exists to enforce: **a file replaces the user's shortcuts only after it has proved what it
is, proved it is undamaged, and been read end to end.** Nothing is touched before all three hold.

- **File format v2**: a readable `BackupEnvelope` (FileType, FormatVersion, CreatedUtc,
  CreatedByVersion, Encryption, KDF parameters, `PayloadSha256`) wrapping a base64 `BackupPayload`.
  The envelope stays readable on purpose so the file can identify itself, be dated, and be recognised
  as encrypted BEFORE anyone is asked for a passphrase.
- **Encryption at rest (optional, offered on every export)**: AES-256-GCM, key from
  PBKDF2-SHA256 with a random 16-byte salt and 300,000 iterations, 12-byte nonce, 16-byte tag,
  AAD `"KeyPulseBackup.v2"`. Both the derivation and the write run on a background thread. There is
  no recovery path for a forgotten passphrase and the UI says so.
- **Integrity**: `PayloadSha256` is checked BEFORE the payload is parsed, so a bit-flip or a
  truncation can never reach the shortcut list. `Write` also reads the finished file back and
  re-decrypts it - a backup that cannot be read again is not a backup.
- **Atomic write**: through `AtomicFileWriter.WriteAtomic` with fallback protection.
- **What travels**: every shortcut (including `DisplayName`, `KeyCombinations`, `IsTargetObfuscated`, `AddToQuickActionMenu`),
  the complete Desktop Organizer configuration and profiles (`BackupPayload.DesktopOrganizer`),
  the complete Screen Brightness configuration, hardware bindings, lock states, and presets (`BackupPayload.ScreenBrightness`),
  the browser/sound/theme/typing-speed/sort preferences, `HasSeenTrayHint`, and the full window
  layout - main, Settings and Setup geometry plus all four column widths.
- **What deliberately does NOT travel**: `AppConfig.LaunchOnBoot`. Whether KeyPulse starts with
  Windows is a property of the machine (a registry value or a scheduled task), and silently turning
  it on because a backup from another PC had it on would be an unpleasant surprise. Restore says so.
- **Targets are exported in plain form inside the payload**, on purpose: on disk they are DPAPI-bound
  to this Windows account (see below), so a protected copy could never be restored anywhere else -
  which is the one case backups exist for. Protection for the FILE is the passphrase.
- **Geometry is validated against the CURRENT machine** (`ApplyRestoredWindowLayout`): sizes are
  clamped to the working area, a position is used only when it lands on a monitor that is actually
  attached, and `Minimized` is never restored. A position from a three-monitor desk would otherwise
  open the window somewhere the user cannot reach, which looks exactly like the app failing to start.
- **Corruption vs. machine differences**: `ValidatePayload` refuses the WHOLE file for structural
  damage (an action code outside `ActionType`, a null row, a failed checksum) and imports-and-flags
  anything that is merely different about this PC (keys already taken, a missing folder, a
  combination this build cannot parse). Rejecting a file for the second kind is what made restore
  useless on a new PC.
- **Backwards compatibility**: every backup taken by an earlier build is a raw copy of `config.json`.
  `Inspect` recognises those, decrypts their legacy `ENC:` targets, and upgrades them. The guard that
  keeps this from reopening the old data-loss hole is a `JsonDocument` shape check: a `"Hotkeys"`
  array must be PRESENT IN THE FILE. A deserializer's default empty list is never good enough.
- **Rollback**: `ConfigStore.SaveRollbackCopy("before-restore")` writes a dated copy first (five kept)
  and the path is reported to the user. Any exception during import restores the previous snapshot;
  if the rollback itself fails, the message names the file to rename by hand.

### Desktop Organizer (`DesktopOrganizerService.cs` & `DesktopOrganizerWindow.axaml.cs`)
- **Multi-Monitor Layout Management**: Captures and restores desktop icon coordinates across single and multi-display setups. Layout profiles are persisted to `%APPDATA%\KeyPulse\desktop_organizer.json`. Cross-monitor proportional scaling runs whenever saved monitor bounds are present (`profile.Monitors.Count > 0`), even if the current monitor count differs from when the profile was saved. Features 4 customizable placement options for unsaved new icons: Center of primary screen (Default), Untouched in place, Align down right side, and Center of secondary monitor.
- **Atomic Persistence, LKG Redundancy & Empty-Overwrite Guard**: `SaveConfig` utilizes `AtomicFileWriter.WriteAtomic`, copies the existing valid `desktop_organizer.json` to `desktop_organizer.lkg.json` before overwriting, and updates `desktop_organizer.lkg.json` after each verified write. `DesktopOrganizerWindow` sets `_suppressConfigEvents = true` before `InitializeComponent()` (and omits static `SelectedIndex` in XAML) so initial control construction cannot trigger a premature save before `LoadConfig()` completes. Furthermore, `SaveConfig(config, allowEmptyProfiles)` refuses to overwrite a non-empty on-disk profile list with an empty in-memory list unless `allowEmptyProfiles: true` is explicitly passed from the user's `Delete` action.
- **Inline Profile Renaming & Non-Overlapping Profile Cards**: Each profile card uses a `WrapPanel` with clipping constraints so badges (`MANUAL (Protected)` vs. `AUTO-SNAPSHOT (x/5)`, `ACTIVE`) wrap fluidly without overflowing into column 1 or overlapping `Restore Layout` buttons. Inline renaming activates a dedicated rename editor row with explicit `[Save]` and `[Cancel]` buttons (in addition to `Enter`/`Escape` keybindings) so users never feel trapped.
- **Configurable Periodic Auto-Snapshots**: When `AutoPeriodicSnapshotEnabled` is checked, `EnsureAutoSnapshotScheduler()` runs an initial check (after a 15-second startup delay) and a 6-hour background timer to capture automated snapshots on a customizable day interval (`AutoSnapshotIntervalDays`, `1–30 days`, default 3 days) with an interactive stepper (`− / +`). Auto-snapshots skip execution if fewer monitors are connected than previously seen or if no icon moved by more than 4 pixels compared to the newest snapshot, and automatically prune only the oldest auto-snapshot beyond `MaxAutoSnapshots = 5` while **never** auto-deleting user-created manual profiles.
- **Corrupt Profile Quarantine & Graceful Recovery**: Load failures return a typed `DesktopOrganizerLoadResult` without erasing in-memory profiles. If `desktop_organizer.json` is corrupted, it is quarantined to `desktop_organizer.damaged-<timestamp>.json` and automatic recovery from the LKG backup is attempted. If recovery fails, the UI enters Read-Only mode to protect surviving profile state from accidental overwrite.
- **Pre-Wipe Safety Preservation**: Desktop Organizer profiles are included in the setup wipe safety system via `ConfigStore.SaveAllWipeSafetyCopies()` and backup envelopes.
- **Auto-Arrange Guard**: `RestoreLayout` verifies `IsAutoArrangeActive(out bool desktopVisible)` upfront, warning the user and aborting restoration if Windows Auto-Arrange is enabled.
- **Boundary Clamping**: Anti-collision icon coordinate displacement contains horizontal boundary checks (`maxX` and `minCurX` wrap/clamp) to prevent icon displacement beyond visible monitor coordinates.
- **Non-Blocking Explorer Shell Interop**: Icon position queries and desktop updates communicate via Win32 `SendMessageTimeout` with a 500 ms limit and `SMTO_ABORTIFHUNG` flag to prevent UI thread lockups if Explorer hangs.
- **Theme Awareness & Audio Feedback**: Resource brushes resolve dynamically against `app.ActualThemeVariant` within `ThemeDictionaries`. Interactive feedback relies strictly on embedded assembly assets (`click.wav`).

### Screen Brightness & Contrast Control (`ScreenBrightnessService.cs`, `ScreenBrightnessOverlayWindow.cs`, `ScreenBrightnessWindow.cs`)
- **Active-Display-Only Dynamic Layout (Max 3 Displays: Screen A, Screen B, Screen C)**: Both the full configuration window (`ScreenBrightnessWindow`) and the borderless auto-closing tray overlay (`ScreenBrightnessOverlayWindow`, clamped to the DPI-scaled `WorkingArea` with a 12 px margin and dismissed on `Deactivated` or `Escape`) dynamically query connected physical monitors (`GetConnectedSlotIndices`) and display only currently connected, active displays. Inactive/disconnected slots are hidden rather than displayed as disabled placeholders. The overlay window automatically resizes its width dynamically (`420 px` for 1 screen, `540 px` for 2 screens, `680 px` for 3 screens).
- **Dual Vertical Sliders & Lock Ratio**: Each active screen container houses two vertical sliders (`0–100`): left for **Brightness**, right for **Contrast**, with bold live numeric readouts directly above each slider, Mouse Wheel (`±2`) and Up/Down Arrow support, and a per-screen **Lock Ratio** checkbox underneath (governed globally by the default-ON **Lock Brightness & Contrast Together Tight** setting). When locked, moving either slider moves the other to the exact same value immediately; re-checking **Lock Ratio** immediately snaps Contrast to match Brightness's current value.
- **Hardware DDC/CI & NativeAOT Laptop Backlight Control**: External monitors are controlled via `dxva2.dll` (`GetNumberOfPhysicalMonitorsFromHMONITOR`, `GetPhysicalMonitorsFromHMONITOR`, `GetMonitorBrightness`, `SetMonitorBrightness`, `GetMonitorContrast`, `SetMonitorContrast`) with every physical monitor handle guaranteed to be released via `DestroyPhysicalMonitors` inside a `finally` block. Internal laptop displays are controlled via NativeAOT-safe Win32 `\\.\LCD` kernel `DeviceIoControl` (`IOCTL_VIDEO_QUERY_SUPPORTED_BRIGHTNESS`, `IOCTL_VIDEO_QUERY_DISPLAY_BRIGHTNESS`, `IOCTL_VIDEO_SET_DISPLAY_BRIGHTNESS`) bound strictly to primary display Slot 0. Hardware `Min..Max` ranges are normalized to a `0–100%` percentage scale with no artificial minimum floor (`0%` maps to hardware `Min`).
- **Non-Blocking Parallel Live Read & User-Touch Priority**: Opening the sliders renders cached values in `0 ms` (`GetImmediateCachedStates`) and queries physical monitors in parallel on background threads (`ReadAllScreensLiveAsync`). Touching, dragging, or scrolling a screen's slider sets a per-screen user-touch flag (`ScreenContainerView.UserTouched = true`) that cancels/ignores the initial background read for that screen so late hardware replies never jump the slider back.
- **250 ms Hardware Speed Limiter, Trailing-Edge Flush & Delta-Only Writes**: Slider movements are throttled per screen to at most one hardware write every `250 ms` (`RequestScreenLevelChange` / `QueueThrottledHardwareWrite`), with a guaranteed trailing-edge flush (`ExecutePendingWriteForSlot`) when the 250 ms window ends so the physical monitor always receives the final number. Hardware writes skip any screen whose target Brightness and Contrast match its last applied hardware values (delta-only writes) to prevent backlight flicker.
- **Stable Hardware ID Binding, Inline Screen Renaming UX & Click-Through Identify Banners**: Screen slots (`A`, `B`, `C`) bind to each display's EDID/GDI `HardwareId` + `DeviceKey` + `ModelName` (`BindMonitorsToSlots`) so identical models, cable swaps, or reboots do not collide. Renaming a screen container reveals an inline `TextBox` accompanied by explicit `✓` (Save) and `✕` (Cancel) action buttons, displays clear visual confirmation on save, and auto-commits when clicking anywhere outside on the card or window. `ShowIdentifyBanners()` flashes non-activating click-through (`ShowActivated = false`, `WS_EX_NOACTIVATE | WS_EX_TRANSPARENT`) identification overlays on each active physical monitor without stealing focus.
- **Multi-Screen Shortcut Key Cycling (`ActionType.CycleBrightness`) Edge Case Resilience**: Brightness presets enabled for `IncludeInCycle` (`GetOrderedCycleProfiles`) are ordered by active display brightness. Pressing a `CycleBrightness` hotkey (`TriggerShortcutCycleStep`) starts at the lowest preset on the first press of the session (`_hasStartedCycleInSession`), climbs up to the highest on subsequent presses (`LastCycleProfileId`), and wraps back to the lowest. If a user configured a 2- or 3-display cycle but only 1 display is currently connected, `TriggerShortcutCycleStep` intelligently filters and skips presets that have identical levels on the currently active display, ensuring the shortcut never gets stuck on dead no-op keypresses. Dispatches only to connected slots on background threads with zero OSD popups or focus changes.

### Data Persistence (`Models.cs`, `ConfigStore.cs`, `CryptoHelper.cs`, `AtomicFileWriter.cs`, `IpcService.cs`)
- State is managed via the `AppConfig` class, stored at `%APPDATA%\KeyPulse\config.json`, alongside `DesktopOrganizerConfig` (`%APPDATA%\KeyPulse\desktop_organizer.json` / `.lkg.json`) and `ScreenBrightnessConfig` (`%APPDATA%\KeyPulse\screen_brightness.json` / `.lkg.json`). When `Program.IsDevMode` is true (`DEVDATA_01`), `ConfigStore.ConfigDirectory` (and `ScreenBrightnessService.AppDataFolder`) routes all configuration, Desktop Organizer layouts, and Screen Brightness presets to `KEYPULSE_DEV_DATA_DIR` / `%LOCALAPPDATA%\KeyPulse_DEV\data` (with clean-baseline snapshots persisted in `%LOCALAPPDATA%\KeyPulse_DEV\keep`), guaranteeing zero cross-contamination with `%APPDATA%\KeyPulse`.
- **Target protection**: `CryptoHelper` uses **DPAPI (`ProtectedData`, CurrentUser scope)** with a fixed entropy string and writes a `DPAPI:` prefix. The old `ENC:` AES format, whose key and IV were hard-coded in the executable, is still READ for migration and never written again. `TryUnprotect` returns **false** on failure and the row is flagged `TargetUnreadable`; it must NEVER return the cipher text, which is how a shortcut's target silently became the literal string `ENC:8Kd2...`.
- **`ConfigStore` is the ONLY reader/writer of that file.** It writes atomically through `AtomicFileWriter.WriteAtomic`, and on a damaged/unreadable file it **renames the file aside** as `config.damaged-<timestamp>.json` and reports the problem. Nothing in this codebase may `File.Delete` or blind-overwrite the config: doing so is how every shortcut used to vanish silently.
- **Atomic File Writing (`AtomicFileWriter`)**: Shared atomic writer utility employing `.tmp` staging, multi-attempt Win32 `File.Replace` with backup, and atomic `File.Move(overwrite: true)` fallback. Never falls back to non-atomic `File.Copy`.
- **Named Pipe IPC (`IpcService`)**: Low-integrity SDDL (`D:(A;;GA;;;WD)S:(ML;;NW;;;LW)`) Named Pipe server/client (`KeyPulse_IPC_Session_<SessionId>`, or `KeyPulse_IPC_DEV_Session_<SessionId>` in Dev Mode) for shell context-menu "Add to KeyPulse" requests, providing length-prefixed framing and synchronous acknowledgment without file-based collision races.
- Holds an array of `HotkeyEntry` objects (DisplayName, KeyCombinations, ActionType, Target string, `IsTargetObfuscated`, `AddToQuickActionMenu`) alongside UI bounds, desktop organizer profile configurations, and screen brightness configurations.
- **Serialization Constraint**: As the app is `NativeAOT`, reflection-based JSON serialization is forbidden. `JsonSerializerContext` source generators (`AppConfigJsonContext`) are strictly enforced. All floating-point numbers support named literals (`AllowNamedFloatingPointLiterals`).

- **NEVER report Administrator mode as active without checking `Program.IsElevated`.** `/RL HIGHEST` succeeds on accounts that cannot actually elevate.

- **NEVER create or update `KeyPulse_AdminTask` without stripping battery constraints (`DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` set to `false`).** Windows Task Scheduler defaults to disallowing execution on battery power, breaking autostart on laptops.

- **NEVER lose elevated privilege state across upgrades when "Keep Settings & Upgrade" is selected.** Query running process tokens before terminating and relaunch with `runas` upon setup completion.
- **Windows Only**: Do not attempt to introduce Linux/macOS cross-platform polyfills. The app's architecture explicitly leverages Windows-only DLLs (`user32.dll`, `kernel32.dll`, `dxva2.dll`).

- **Developer Sandbox Root (`DEVDATA_01`, Dev Mode Only):** `%LOCALAPPDATA%\KeyPulse_DEV` (`data\` for live sandboxed `config.json`, `desktop_organizer.json`, and `screen_brightness.json`; `keep\` for clean-baseline state restoration across `dev.cmd` runs; `runtime\` for isolated dev native libraries; `%TMP%\KeyPulse_DEV` or `.devlogs\` for dev logs; and `\\.\pipe\KeyPulse_IPC_DEV_Session_<SessionId>` for dev IPC).

### Legacy / Deprecated Paths (Must be cleaned up by Installer/Uninstaller)
- `C:\Program Files\KeyPulse` (Abandoned global install directory)
- `C:\Program Files (x86)\KeyPulse` (Abandoned global install directory)
- `%TEMP%\KeyPulse_NativeLibs` (Legacy temporary native library extraction folder, superseded by the `runtime` subfolder)
- `%TEMP%\KeyPulse_Runtime` (`Program.RuntimeFallbackDir` - fallback extraction folder, used only when the install directory is not writable. Cleaned by `RunUninstall` AND by the uninstall self-delete script, which targets this **and** `KeyPulse_NativeLibs`: the legacy folder is still removed on purpose, because an upgrade from an older build leaves one behind.)
- `%LOCALAPPDATA%\KeyPulse` (Legacy log folder holding `keypulse_debug.txt` / `keypulse_crash.txt`. No uninstaller ever removed it, so a record of every shortcut the user pressed survived uninstalling. Both the installer and the uninstaller now delete it.)
- `%TEMP%\KeyPulse*.exe` (Legacy temporary execution binaries)
- `%TEMP%\keypulse_*.txt` (Legacy temporary installer log files)
