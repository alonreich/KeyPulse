## 1. PROJECT OVERVIEW
**KeyPulse** is a lightning-fast, ultra-lightweight Windows hotkey manager designed for power users. 
- **Tech Stack**: C# 13, .NET 9, Avalonia UI 12.1.
- **Compilation**: Single-file `NativeAOT` (No .NET runtime dependencies).
- **OS Target**: Windows x64 Strictly (Heavily relies on Win32 P/Invoke).

## 3. GLOBAL DIRECTIVES (APPLY TO EVERY CHANGE)
- **MANDATORY CHANGELOG DIRECTIVE**: record every technical change under `## [Unreleased]` in `docs/changes.md`; add plain-English user impact under `## [Unreleased]` in `docs/CHANGELOG.md`.
- **NEVER use reflection**: This is a NativeAOT app. Use Source Generators for JSON, Regex, or interop.
- **NEVER allow Dev Mode (`Program.IsDevMode` / `DEVDATA_01`) to read or write `%APPDATA%\KeyPulse`, `%LOCALAPPDATA%\Programs\KeyPulse`, `HKCU\...\Run\KeyPulse`, or `KeyPulse_AdminTask`.** All dev state, runtime DLLs, logs, mutexes, events, and IPC pipes must stay isolated under `%LOCALAPPDATA%\KeyPulse_DEV`, `%TMP%\KeyPulse_DEV`, and `_DEV`-suffixed kernel objects.
- **NEVER mix UI Threads**: Callbacks from `HotKeyManager` execute on a raw background thread. Any modification to Avalonia UI elements during a hotkey trigger MUST be wrapped in `Dispatcher.UIThread.Post(() => { ... })`.
- **NEVER delete or blind-overwrite `config.json`.** Route every read/write through `ConfigStore`.
- **NEVER use non-atomic `File.Copy(..., overwrite: true)` for configuration or state persistence.** Always route atomic file writes through `AtomicFileWriter.WriteAtomic`.
- **The app manifest declares PerMonitorV2 DPI awareness.** Do not remove it; the UI becomes bitmap-stretched and blurry.
- **Windows Only**: Do not attempt to introduce Linux/macOS cross-platform polyfills. The app's architecture explicitly leverages Windows-only DLLs (`user32.dll`, `kernel32.dll`, `dxva2.dll`).

## 4. CRITICAL HARDWARE PROTECTION & I2C/DDC BUS GUARD RAILS (MANDATORY DISCLAIMER)
> [!CAUTION]
> **MANDATORY HARDWARE PROTECTION PROTOCOL (FOR ALL AI AGENTS & DEVELOPERS):**
> The Screen Brightness subsystem interfaces directly with physical monitor scaler microcontrollers over the GPU I2C bus (DDC/CI via `dxva2.dll`) and laptop backlight hardware (`\\.\LCD`). Hardware microcontrollers (MCUs) run on low-speed embedded clock cycles and have zero tolerance for race conditions or packet floods. Any regression of the following guard rails can cause physical monitor MCU lockups, EEPROM/scaler register corruption, backlight flickering, display driver crashes, or SSD disk thrashing. These constraints are NOT performance suggestions; they are mandatory safety invariants:
>
> 1. **SEQUENTIAL MULTI-DISPLAY WRITES ONLY (`Parallel.ForEach` IS STRICTLY FORBIDDEN)**:
>    Multi-monitor profile applications (`ApplyProfileToHardwareDeltaOnlyAsync`) MUST run sequentially in a single `foreach` loop over deterministically sorted slot indices (`bound.Keys.OrderBy(k => k)`). The GPU's display controller I2C bus multiplexer CANNOT service concurrent transactions across distinct physical ports simultaneously. Concurrent writes trigger hardware bus collisions and driver deadlocks.
>
> 2. **MANDATORY 30 MS INTER-DISPLAY SETTLING DELAY**:
>    Between distinct physical display writes in `ApplyProfileToHardwareDeltaOnlyAsync`, a delay of `await Task.Delay(30)` (non-blocking) MUST be enforced. This allows the GPU display multiplexer and I2C lines to settle between physical addresses. Every iteration must check `token.IsCancellationRequested` before and after the delay.
>
> 3. **MANDATORY 50 MS DDC/CI COMMAND SPACING, READ-BEFORE-WRITE & BOUNDED RETRY**:
>    Every DDC/CI command (read or write) MUST be separated by `DdcWriteSafety.CommandSpacingMs = 50`. All monitor writes MUST go through `DdcWriteSafety.WriteFeatureAsync` (sync `WriteFeature` is a test-only twin with the same policy): read first, never write without a confirmed hardware range, skip values the monitor already holds, and send at most one high-level set plus one raw VCP fallback. Failed writes MUST NOT be auto-retried; only `VCP 0x10` / `0x12` may ever be written. Tests MUST NOT reach physical monitors (`IsTestExecutionEnvironment()` guard / `HardwareWriteOverrideForTesting`).
>
> 4. **STRICT HARDWARE RAW CLAMPING & CONTRAST FLOOR**:
>    Raw values MUST stay strictly within the range the monitor reported (`DdcWriteSafety.ToRaw`). Brightness 0% maps to the hardware minimum; contrast 0% maps to `min + 5%` of the range (`MinContrastFloorPercent`) so the image never goes fully black.
>
> 5. **PER-SCREEN SETTLE-BASED WRITE SCHEDULER (NVRAM WEAR LIMITER), TRAILING-EDGE FLUSH & THROTTLE DEADLOCK GUARD**:
>    Continuous input MUST be written only once it settles (`SettleMs = 500`) or at most every `MaxLatencyMs = 1500` during uninterrupted input; isolated changes write immediately (`DdcWriteSafety.DecideSchedule` / `ComputeFlushDelayMs`, `RunSettledFlushAsync`). The final selected value MUST always reach hardware. Crucially, `throttle.LastWrittenBrightness` and `LastWrittenContrast` MUST update ONLY when `written == true`. Recording failed hardware attempts as successful permanently deadlocks future writes due to delta-only write suppression.
>
> 6. **DECOUPLED DISK PERSISTENCE (ZERO DISK THRASHING ON SLIDER DRAG)**:
>    Synchronous disk writes (`SaveConfigInternal`) inside real-time slider drag handlers (`RequestScreenLevelChange`) are STRICTLY FORBIDDEN. Moving a slider must ONLY mutate in-memory state (`slotCfg.LastBrightness`, `slotCfg.LastContrast`). Disk writes occur exclusively in the background trailing-edge flush in `ExecutePendingWriteForSlotAsync` (`Task.Run`) once motion settles, and deterministically on window closure via `ScreenBrightnessService.FlushConfig()`.
>
> 7. **DELTA-ONLY HARDWARE FILTERING**:
>    Never dispatch writes to hardware if `targetB == prevB && targetC == prevC`. Skipping unchanged values prevents backlight pulsing and unnecessary I2C bus traffic.
>
> 8. **DETERMINISTIC MONITOR HANDLE DESTRUCTION**:
>    Every handle returned by `GetPhysicalMonitorsFromHMONITOR` MUST be freed via `DestroyPhysicalMonitors` in a `finally` block to prevent GDI/kernel handle leaks that exhaust OS-wide DDC/CI resources.
