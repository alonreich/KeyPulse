# Hotkey Interception & Input Automation

> Read `project_structure.txt` (mandatory rules + hardware guard rails) before this file. Route: [`docs/index.md`](../index.md).

## Hotkey Interception (`HotKeyManager.cs`)
- **Background Win32 Loop & Broadcast Message Processing**: Spawns a dedicated background thread constructing a top-level hidden unowned Win32 window (`CreateWindowEx` with parent `IntPtr.Zero` instead of `HWND_MESSAGE`). This allows the window to intercept both targeted window messages and OS-wide broadcast messages, specifically `WM_DISPLAYCHANGE` (`0x007E`) and `WM_POWERBROADCAST` (`0x0218`), triggering automatic DDC/CI display scaler wake handshakes and debounced desktop icon re-layout upon display reconnection or sleep wake.
- **Native Intercepts**: Uses `RegisterHotKey` and `UnregisterHotKey`. Traps `WM_HOTKEY` events globally across the OS, translating the integer ID back into a C# `Action` callback.
- **`RunOnThread` owns its signal, the caller does not**: the `ManualResetEventSlim` is disposed by the queued task, not by a `using` in the waiter. A timed-out wait used to dispose it while the task was still queued, so `Set()` threw into the message loop's empty catch and the work completed silently AFTER the caller had reported failure - leaving the status column disagreeing with what Windows had actually done.
- **RunOnThread is transactional (no ghost registrations)**: each queued item carries an atomic state (Pending/Running/Cancelled/Completed/Abandoned). A caller that times out while the item is still Pending cancels it, so the hotkey thread skips it and never calls RegisterHotKey. A caller that times out while it is Running abandons it, and the hotkey thread runs the onAbandoned rollback (Register uses it to UnregisterHotKey and drop _actions/_activeCombos entries). A alse return therefore always means no OS registration exists. The signal is never disposed (the waiter may still be in Wait). RunOnThreadTimeoutMs / RunOnThreadForTesting are test seams; covered by HotkeyManagerGhostRegistrationTests.
- **Probe Functionality**: Dynamically checks combinations against an internal `_activeCombos` tracker. If KeyPulse already owns the hotkey, it successfully greenlights it. Otherwise, it tests OS-level availability by registering/unregistering a dummy ID.
- **Capture Mode (CRITICAL)**: there is no low-level keyboard hook. Shortcut capture reads Avalonia `KeyDown` events in the KeyPulse window itself, so it can never swallow keystrokes meant for another application. `IsCaptureMode` is a flag set by `EnableCaptureHook()` / `DisableCaptureHook()` (on `KeyCombo` focus and lost focus, and on window `Deactivated`) and suppresses the 30-second retry timer (`RetryBrokenShortcuts`) while the user is typing a combination. `GetModifierSnapshot` reads live modifier state via `GetAsyncKeyState`.

## Automation Engine (`InputSimulator.cs`)
- Handles execution of user actions.
- **Win32 `SendInput`**: Injects real hardware **scan codes** (`KEYEVENTF_SCANCODE` with `wVk = 0`) for the `TypeText` action, in batches. Virtual-key-only injection was invisible to games, RDP sessions and VMs, so the shortcut appeared to do nothing at all. Every injected event carries `InputSimulator.InjectionTag` in `dwExtraInfo` so the capture hook can recognise and ignore KeyPulse's own output.
- **Keyboard layout (CRITICAL)**: `GetTargetKeyboardLayout()` asks the FOREGROUND window's thread which layout it uses. `GetKeyboardLayout(0)` answers for KeyPulse's own thread and produced scrambled text whenever the target app was on a different layout. Never go back to `GetKeyboardLayout(0)`.
- **Typing speed**: `InputSimulator.CharacterDelayMs` mirrors `AppConfig.TypingDelayMs` (Fast 1 / Normal 6 / Compatible 18 ms) and characters are sent in batches. The old fixed 12 ms sleep after every character locked the keyboard for over half a minute on a 3,000-character snippet, with no setting to change it. Runs are single-flight (`IsTyping` gate), cancellable (Esc or `CancelTyping()`), and raise `TypingStarted` / `TypingProgressChanged` / `TypingFinished` so the UI can show a non-activating progress window.
- **Clipboard backup has a TOTAL budget**, not just a per-format one: `ClipboardBackupBudgetBytes` (16 MB) on top of `ClipboardSingleFormatLimitBytes` (16 MB). One large image is offered by Windows in several formats at once, so a bounded limit prevents copying tens of megabytes aside on the Large Object Heap on every press. Anything over budget is reported through the existing `warning` out-parameter.
- **Clipboard Owner HWND & Sequence Safety**: Clipboard ownership is prioritized to the long-lived, dedicated message-loop handle (`HotkeyManager.MessageWindowHandle`) protected by `_clipboardHwndLock` with Win32 `IsWindow` validation, safely falling back to `IntPtr.Zero` (task-level ownership) if uninitialized. Ephemeral ThreadPool worker window creation is eliminated, preventing handle invalidation (`ERROR_INVALID_WINDOW_HANDLE` 1400) and paste starvation. Before restoring backed-up clipboard content after paste simulation, `GetClipboardSequenceNumber()` is checked; if another application placed new content on the clipboard during injection, restore is aborted to prevent clobbering user data.
- **Clipboard Injection**: `InsertText` enumerates clipboard formats but only backs up **HGLOBAL (moveable memory) formats**. GDI-handle formats (`CF_BITMAP`, `CF_PALETTE`, `CF_METAFILEPICT`, `CF_ENHMETAFILE`, the `CF_GDIOBJ*` range) are NOT memory blocks; byte-copying them destroyed the user's clipboard. They are skipped and reported to the user via the `warning` out-parameter. `CF_DIB`, `CF_DIBV5` and `CF_HDROP` ARE memory and survive intact.
- **Paste timing & Starvation Prevention**: after `Ctrl+V`, `WaitForClipboardToBeConsumed(300)` polls `GetOpenClipboardWindow()` until a foreign process has opened and closed the clipboard (300 ms cap with 5 ms / 15 ms throttled polling) before restoring. This prevents worker thread starvation and eliminates false "busy" paste rejections while allowing slow apps to consume the clipboard reliably.
- Avalonia's built-in clipboard is purposefully abandoned to prevent `Dispatcher.UIThread` deadlocks.

## Directives

- **NEVER restore clipboard without checking `GetClipboardSequenceNumber()`.** If external content was copied during text injection, skip restore.
